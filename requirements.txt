# ── CRITICAL deps: upper bounds are LOAD-BEARING ────────────────────────────
# Railway resolves requirements at BUILD time, so an open `>=` lets a new MAJOR
# in on any rebuild — days after the code that "works" was written, and only in
# prod (local dev keeps the old resolved version). That is exactly how the whole
# broker fleet died on 2026-07-23 (see the snaptrade pin below): the SDK took
# credentials as **kwargs, a major bump silently swallowed them, and every
# request went out unauthenticated with NO exception raised.
#
# Auditing the rest on 2026-07-23 found FOUR more that had ALREADY crossed
# majors unnoticed in production — they simply happened not to break:
#   stripe        >=8.0.0  -> running 15.3.1   (payments + webhooks)
#   cryptography  >=43.0.0 -> running 49.0.0   (Fernet = broker secret decrypt)
#   bcrypt        >=4.1.0  -> running 5.0.0    (password hashing)
#   websockets    >=12.0   -> running 16.1.1   (live bars + OPRA consumer;
#                                               13/14 reworked the asyncio API)
# Bounds below are set at the CURRENTLY-RUNNING major, so a rebuild can never
# silently cross another one. Raising a bound is a deliberate act: read that
# project's migration notes, then re-validate our call sites.
# Guarded by tests/test_requirements_pins.py.
