## Notes (non-blocking)
1. MEDIUM, sandbox.mjs:40 REMOVED_PROCESS omits process.getBuiltinModule (present on Node >=20.16, so on the 20.18 pin). After a VM
   escape it is a synchronous module loader (node:net etc.), the very door L3 means to close. It adds no reach beyond dynamic
   import() (syntax, undeletable), and L4 blocks fs-write/spawn, so network denial rests on L1+VM as the design already states -
   but it is a one-word hardening: add 'getBuiltinModule' to REMOVED_PROCESS and to the L3 rail.
2. LOW, pool.mjs:59 workers = availableParallelism(). Node 20's libuv does not read a cgroup CPU quota, so on a Railway container this
   can be the host's core count (design sizing assumes 2 workers x ~300 MB). T10/T9 should pass an explicit worker count.
3. LOW, pool.mjs:148-155 a replacement worker that fails to boot after startup sets `broken` permanently (every run -> 500) and does not
   drain the queue (jobs then time out as server-busy). Fail-closed, but /ready does not consult pool.ready() yet (T9 must).
4. INFO, job.mjs:69-87 encodeColumn is a second copy of T3's canonical column encoding; T3 was not in this base. T7b leaves it in place
   (see W5-T7b.md); the coordinator should collapse it onto the bundle's columnDigest.encodeColumn/bytesToB64.
5. INFO, the service passes budgetMs = RUNTIME_PANE_TIME_BUDGET_MS (1000 ms) per job, as the browser worker does (HP-7 agrees). Correct for
   parity, but on a loaded pod large/32k-bar jobs will withhold as runtime:time-budget; T9's capacity numbers should measure the rate.
6. INFO, probeVerdictCache is keyed by two 32-bit FNV passes; now process-shared across owners (was per-browser). A crafted collision
   could flip another tenant's calc_bars verdict. Low practicality; consider a sha256 key when T2 touches it.
