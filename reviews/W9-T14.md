## Gating and security

- **What keeps the route at 404 in production.** `_require_open` (pine_strategy_backtest.py) calls the existing `runtime_definitions.server_permitted(role, id)`. That function admits nobody unless both of these admit the caller:
  - `PINE_RUNTIME_STAGE`, through `pane_permitted`;
  - `PINE_RUNTIME_SERVER_STAGE`.

  Both are read per call. Both default to `off`. Each value is stripped and lower-cased, and anything outside {off, admins, cohort, all} is treated as `off`. No new flag or variable is added. `main.py` mounts the router unconditionally so that E-3 walks it.
- **Proved by a test I ran.** The test drives the real `server_permitted` over HTTP with real env values, using `tests/_rev_gate_probe_test.py`, which is kept in the scratchpad as `rv/test_rev_gate.py`. 236/236 passed.
  - Server stage values tried: unset, `""`, `"   "`, `of`, `admin`, `ADMINS-`, `everyone`, `1`, `true`, `on`, `yes`, `al l`, `None`, `null`, `\tadmin\n`.
  - Each was crossed with pane stage values (unset, `""`, `all`, `admins`, `bogus`) and with member, admin and no-role users.
  - Every combination returns `404 {"detail":"Not Found"}`. Defs, bars, the client and the plan check are never touched.
  - Server `all` with the pane unset, empty, `off` or a typo is 404 for every user, and so is the pane at `all` with the server off.
  - At `admins`/`admins`, a member or a caller with no role gets 404, and an admin gets past the gate.
  - A dark request with a malformed body is 404, not 422.
  - Control: with both stages at `all`, the request reaches the plan check and then the defs lookup.
- **Auth order.** `get_current_user_with_plan` (401) runs, then the dark gate (404), then the plan gate (402), then any read. An unauthenticated request is 401 with nothing touched. One consequence is that an unauthenticated caller sees 401, not 404, while the route is dark, so the route's existence is visible (N4). That follows from the brief's requirement that auth run first.
- **Bounded compute.**
  - Symbols are deduped and capped at `min(INLINE_MAX_SYMBOLS=50, max_cells()//HISTORY_WINDOW_BARS)`, with 413 above that. I posted 5,000 symbols: 413, with no bars read and no client call.
  - The cap runs after a single defs read.
  - Each symbol reads at most `HISTORY_WINDOW_BARS` bars.
  - The service call uses profile `backtest`: 60 s deadline, 0 busy retries, and the service's `MAX_JOBS=500`.
  - Inputs are bounded by the client's `_inputs_of`: 256 keys, names up to 128 chars, strings up to 4,096.
  - The route falls under the declared `/api/pine` rate-limit family.
  - There is no app-wide request-body limit, but that predates this lane and applies to every route (N5).
- **No config change.** The diff touches no Railway, `.env`, Docker/compose, toml/yaml or `feature_flags.json`. The only new `process.env` read is `W9T14_WRITE_FIXTURE`, a fixture-regeneration switch inside a `__tests__` file.
- **Second dark layer.** The service never registers the broker gate (railed), so even an armed route answers `pine:strategy-call` by name.
- **Existing API behaviour.** The one behaviour change is in `screener_backtest._runtime_descriptor`: a document stamped `strategy-window` now refuses `runtime:strategy-start` (409). Only `memberPaneDefinition.js:1860` writes that stamp, and only when `probe.broker === true`, which needs the broker gate on. No production document carries it today. Unstamped documents behave as before (railed with a control).

## Notes

- **N1 (before arming): G3 survives the builder's suite.** The builder's `world` fixture replaces `server_permitted` with a lambda that ignores its arguments, so nothing checks that the route passes the caller's own role and id. With the stage at `admins`, that mutant would open the route to every member. Add a rail that uses the real `server_permitted`: at `admins`/`admins`, a member gets 404 and an admin passes. My probe's `test_admins_stage_admits_admin_not_member` kills it.
- **N2 (before arming): W1 survives.** No test feeds a record whose `window.startTime` differs from the start that was sent, so the start part of the one-authority check is unrailed. Add a parametrised case alongside `test_one_authority_a_record_describing_another_window_is_a_500`.
- **N3: the route shares the server-lane stage.** It has no flag of its own. Arming `PINE_RUNTIME_SERVER_STAGE` (and the pane stage) for alerts and scans also opens this route to the same audience. It would still answer `pine:strategy-call` until the service learns the broker gate, so whoever arms it should know. I did not read the production values of either stage (Railway is out of scope).
- **N4: dark is only 404 to an authenticated caller.** An unauthenticated request gets 401, which shows the route exists. This is acceptable because auth runs first, as required.
- **N5: a member's bad input becomes a 500.** `inputs: dict[str, Any]` accepts nested values. One input the client's `_inputs_of` rejects (a list value, more than 256 keys, or a string over 4,096 chars) withholds every job as `runtime:server-integrity`. `_transport` then turns that into a 500 for the whole request, not a 4xx that names the input. Suggest validating inputs at the route, or mapping that sentence to a 400.
- **N6.** `symbols` has no pydantic `max_length`. The list is parsed in full before the 413, and there is no app-wide body limit (both predate this lane).
- **N7.** The builder's open items stand and were not decided here:
  - how the service learns the broker flag (it conflicts with W5-T2 H3);
  - `historyFromListing` is always false;
  - there are no background receipts (privacy).
