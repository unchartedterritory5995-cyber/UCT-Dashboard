# Sector Strength Voice Tool — Bug Fix Report

## 1. Reproduction

`get_sector_strength` in `api/services/voice_market_tools.py:422-453` (pre-fix):

```python
def get_sector_strength(*, period: str | None = None, count: int = 3) -> dict:
    """Strongest sectors. Period currently snapshot-only (today)."""
    try:
        from api.services.rs_ranking import get_sector_strength as _sec
        rows = _sec() or []
    except (ImportError, AttributeError):
        from api.services.engine import get_themes
        themes = get_themes() or {}
        rows = [{"sector": t.get("name"), "change_pct": t.get("pct")}
                for t in (themes.get("leaders") or [])[:5]]
    ...
```

Confirmed by reading `api/services/rs_ranking.py` in full: it exports exactly
two functions, `compute_rs_scores()` and `get_rs_for_ticker(ticker)`. There is
no `get_sector_strength` anywhere in that module (nor in `api/routers/rs_ranking.py`
— that router doesn't exist; the audit's path was close but the real broken
import is `api.services.rs_ranking`, not `api.routers.rs_ranking`).

`from api.services.rs_ranking import get_sector_strength as _sec` therefore
always raises `ImportError`, and the `except` branch runs unconditionally:

```python
from api.services.engine import get_themes
themes = get_themes() or {}
rows = [{"sector": t.get("name"), "change_pct": t.get("pct")}
        for t in (themes.get("leaders") or [])[:5]]
```

`get_themes()` returns THEME leaders (e.g. `{"name": "Semiconductors", "pct": "+2.5%"}`
— arbitrary market themes like "AI", "Crypto", "Semiconductors"), which get
relabeled with the key `"sector"` and served as if they were GICS sector
strength. The `period` kwarg is accepted but never passed to `get_themes()`
(which does accept a period arg) — so the result is always "today" regardless
of what the caller asked for. Net effect verified: any voice question about
"strongest sectors" gets a confident, wrong answer built from unrelated theme
data, with no error signal anywhere in the response (`"ok": True`).

**A second, independent copy of the identical bug** was found while tracing
callers: `api/services/voice_tool_impls.py:35-59`, a dead/unused helper
`_sector_flow()` (defined "for monkeypatching in tests" per its own comment,
never actually called by the registered `get_sector_strength` tool impl at
line 4002-4004, and not referenced by any test). Same broken import
(`from api.services.rs_ranking import get_sector_strength`), same theme
fallback. Fixed it too since it's the same architectural landmine sitting
dormant — cheap to fix now, expensive to rediscover later if something starts
calling it.

## 2. Root cause + design choice

**Root cause:** `get_sector_strength` was written as a placeholder / stub with a
speculative import path pointing at a function that was never implemented in
`rs_ranking.py`, and an except-ImportError fallback that was clearly meant
to be temporary but shipped to production as the permanent (and silent)
behavior.

**What real sector data exists in the codebase — investigated first:**
- (a) **Sector-ETF relative strength (SPDR XLK/XLF/.../XLC)** — no existing
  computation anywhere (`grep -ri "XLK\|sector_etf\|sector_strength"` across
  `api/` turned up nothing except the broken tool itself). However,
  `CLAUDE.md`'s Data Sources table already documents a "Sector Flow" row —
  *"Massive API 20-day bars for 11 SPDR ETFs | 15min cache"* — meaning this
  exact feature was planned/documented but never actually built. Checked
  `api/data/cap_universe.json`: only 7 of the 11 SPDR tickers are present
  (XLK, XLF, XLE, XLV, XLI, XLRE, XLC present; XLY, XLP, XLB, XLU absent), so
  the universe-wide local `bars_sqlite` prewarm cannot be relied on to have
  all 11 ETFs cached — a live fetch is needed regardless.
- (b) **Existing sector aggregation** — none found.
- (c) **`ticker_metadata`/cap-universe sector fields aggregated over
  `rs_ranking.compute_rs_scores`** — `compute_rs_scores` ranks individual
  *stocks*, not sectors, and per-ticker GICS sector isn't attached to its
  output; aggregating it would mean computing RS for the whole ~3,685-stock
  universe (an expensive, 17s+ operation reserved for the background
  RS warmer per `CLAUDE.md`'s launch-hardening notes) just to derive 11
  sector buckets — needless indirection when sector ETFs already track sector
  performance directly and cheaply (11 tickers, not 3,685).

**Chosen design:** New module `api/services/sector_strength.py` — direct
period-return computation on the 11 SPDR Select Sector ETFs via
`massive.get_agg_bars` (the exact same fetch primitive `rs_ranking.py`
already uses for individual-stock RS, so this follows an established,
approved pattern in this codebase rather than introducing a new one).
- `period` honored via canonical strings `Today`/`1W`/`1M`/`3M` → trading-day
  bar windows `1`/`5`/`21`/`63` (`PERIOD_TO_BARS`), matching the exact period
  vocabulary already advertised in the tool's own parameter schema in
  `voice_tool_impls.py` ("Today, 1W, 1M, or 3M").
- Reused the existing, already-tested `_norm_period()` helper in
  `voice_market_tools.py` (used by `get_theme_status`/`get_theme_laggards`)
  for alias normalization ("quarter" → "3M", etc.) instead of writing a new
  one — one canonical period-parsing implementation in the file.
- 15-minute cache TTL (`_CACHE_TTL = 900`), matching the CLAUDE.md-documented
  target for this exact data source. Empty results are deliberately NOT
  cached, so a transient fetch failure self-heals on the very next call
  instead of freezing "unavailable" for the full 15 minutes.
- `compute_sector_returns(n_bars, *, bars_fetcher=None)` is the pure,
  network-free core (bars source injectable) — unit-testable without mocking
  HTTP; `get_sector_strength(period)` is a thin cached wrapper around it.
- **No fallback of any kind to theme data.** A sector whose bars can't be
  fetched, or don't cover the requested lookback, is silently dropped from
  that period's ranking (not faked); if every sector fails, the function
  returns `[]`, and `voice_market_tools.get_sector_strength` turns that into
  an honest `{"ok": False, "error": ...}` — never re-labeled substitute data.

## 4. Fallback removal — verified

- `api/services/voice_market_tools.py::get_sector_strength` — theme fallback
  deleted; now calls `api.services.sector_strength.get_sector_strength`, wraps
  any exception into `{"ok": False, "error": ...}`, honors `period`.
- `api/services/voice_tool_impls.py::_sector_flow` — same fallback deleted
  (dead code, fixed for consistency/no future landmine).
- Grepped the whole repo post-fix for any remaining
  `rs_ranking.*get_sector_strength` reference: none in runtime code (only in
  a historical plan doc under `docs/superpowers/plans/`, left untouched as it's
  a dated record, not live code).
