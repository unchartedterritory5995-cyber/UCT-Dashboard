# Capability-to-Infrastructure Matrix

## 0. What this document is, and what it is not

**This is NOT the Cross-Product Capability Matrix.** Document B §49 gate item 9 names a `05-product-strategy/capability-matrix/` deliverable (tracked in this program as the future role **F-05**) that compares COMPETITOR products' capabilities against each other and against UCT's — a benchmark-facing artifact, not yet started as of this writing. **This file is a different, complementary artifact**: it maps UCT's OWN proposed capabilities (the system decomposition in `product-architecture.md`) to UCT's OWN existing infrastructure — what data UCT already has, what UCT's backend already computes, what UCT's frontend already exposes, and what licensing constraint sits on top of each. Nobody should cite one file's rows as answering the other file's question. Where a future F-05 author needs a row from here, cite this file's row id rather than re-deriving it.

**Row list and its provenance.** Every row below is one of the 33 systems `product-architecture.md` §4.2 names in its five-tier map: 14 applications (A1–A14) plus one evaluate-only application (E1), 4 edge/chrome systems (S1, S2, S10, S12), 8 platform-core systems (S3–S9, S11), 5 data-platform systems (D1–D5), and the Intelligence Layer (I1). This is the complete row list `product-architecture.md` itself calls "the map" (§4.2) — nothing here adds or drops a system relative to that source; this file only adds the nine-column infrastructure detail product-architecture.md deliberately left to Workstream 3 and this deliverable.

**The nine columns, and what each answers** (architecture principle 7 — six different questions, never conflated, restated here as the column discipline):

| Column | Question it answers |
|---|---|
| CAPABILITY | Which system, from product-architecture.md's row list |
| DATA REQUIRED | What data class(es) the capability needs, independent of who supplies them |
| CURRENT PROVIDER(S) | Data availability (a) — cited by exact row name/number from provider-ledger.md or provider-master-ledger.md, or "none" if no leaf ever found one |
| CURRENT UCT SUPPORT | What already exists — status + UCT-current tag from capability-ledger.md, or the product-architecture.md build-condition tag where the system is new |
| NORMALIZATION NEEDED | Data normalization (b) — is there one internal shape with an identity and a provenance, or per-caller drift |
| BACKEND WORK | Backend capability (c) — what a service must newly compute, serve, or consolidate |
| FRONTEND WORK | UI exposure (d) — what a member-facing or desk-facing surface must newly render or must NOT change (coexistence rules) |
| LICENSING/ENTITLEMENT ISSUE | The rights question, cited to provider-master-ledger.md §2.2/§4 or the licensing register via it — never conflated with technical access |
| REMAINING GAP | What is left after the above four columns, classified honestly as: no gap · consolidation-only · new-provider-needed (with the specific F-09 class-G citation) · deliberately-out-of-scope (citing GOVERNING_PRINCIPLES §13) · or genuinely owner-input-bound (marked PROVISIONAL / OWNER INPUT REQUIRED, never silently decided) |

**Provider citation discipline.** Every non-"none" cell in CURRENT PROVIDER(S) cites a specific row by name and number from `provider-master-ledger.md` §2 (F-09) — e.g. "Massive REST (#1)" — falling back to `provider-ledger.md` (F-03b) row numbers only for the handful of infrastructure providers (Stripe #25, Resend #26, Railway #33) that carry no data-class row in F-09's capability matrix because they are marked `—` (not applicable) there. No provider coverage is invented: where F-09 §3.1 records a capability as class **G** (missing from the stack entirely — nine such capabilities, enumerated there), this file says "none" and classifies the gap using F-09's own §5/§6 checklist rather than asserting a new fact.

**How to read the tier grouping.** Rows are grouped exactly as `product-architecture.md` §4.2 groups them (Applications → Edge/Chrome → Platform Core → Data Platform → Intelligence), because the tier is itself part of the architecture's answer to "what does this capability depend on" — an Application depends on the tiers below it; a Platform-Core system depends only on Data Platform; the reverse dependency is a boundary violation per that document's §3.4.

## 6. Cross-cutting reading of the matrix

**Where a genuinely new vendor is worth evaluating** (the honest, non-inflated list — every other "gap" above resolves through consolidation, retention, or an owner decision, not a purchase):

1. **A9 — a backup/alternative whole-market screener-universe provider.** Finviz Elite is the sole source with no terms document at all and a contested `robots.txt`; this is the single point of failure most likely to delete a core capability outright, not degrade one column.
2. **A7 — a short-interest history provider** (FINRA's free bi-monthly release as a floor, a licensed vendor as the paid option). F-09 §6 item 7 flags this as the one class-G gap where a new vendor *reduces* licensing risk rather than adding it.
3. **A1 — a licensed futures-quotes provider** (NQ/ES/RTY/BTC). The only class-G gap where the incumbent (yfinance) is simultaneously unused-for-licensing-reasons and the sole source; futures positioning is explicitly in scope per GOVERNING_PRINCIPLES §13.

**Where the honest answer is "defer, not buy"** — A4's per-broker estimates, A14's portfolio-risk analytics, D5's M&A/event calendar — each is class-G or owner-timing-bound, and F-09/the Readiness Review already recommend deferral over acquisition for each, for reasons independent of this document.

**Where the gap is entirely internal** — every Platform-Core and Data-Platform row (S3–S9, S11, D1–D5) except S11's own dataset needs zero new vendor spend; the entire "two clearest infrastructure gaps" the Readiness Review names (S3 Entity Master, D1 Provider Abstraction) are pure engineering builds against data UCT already receives.
