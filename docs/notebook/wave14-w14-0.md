### 1.1 The base tour is entry 1 and runs exactly as before

The base tour's runtime is still `tourSteps.js` + `tourCopy.js` + `NotebookTour.jsx` +
`NotebookTourGate.jsx`. Its registry entry only DESCRIBES it: `load()` resolves to the same
`TOUR_STEPS` / `TOUR_STEP_COPY` exports (reference equality, railed), and `startState` for it is
the same `TOUR_START_STATE` object the existing "Take the tour" link uses. NotebookTab filters it
out of the list `RegistryToursGate` receives, so the generic engine never runs it.

The one edit to `NotebookTour.jsx` is code motion: `isOnScreen` and `anchorFor` moved to
`tourAnchorVisibility.js` and are re-exported under the same names. Checked against the base: the
block removed from `git show b06ec4fd85:.../NotebookTour.jsx` appears verbatim in the new module
(a Python substring check over CR-stripped text printed `verbatim`).

### 1.2 The per-track seam (for W14-B)

`tours/index.js` is the only shared file: a track adds `tours/<track>.js` exporting `TOURS`, and
one import line plus one spread here. An explicit list, not `import.meta.glob`, so a node rail can
parse it and a track joins only by a deliberate line. Step data stays lazy (R3): a track exports
thin entries whose `load()` is a dynamic `import()`.

The contract for one tour (full text at the top of `tours/index.js`): `id` (unique, permanent:
the seen-state row is keyed by it), `flag` (the capability's own `notebookFlag` key), `title`,
`replayable`, `load -> {steps, copy}`, optionally `start`. Steps are `{id, anchor, file}`, 3 to 6.
Anchor rule: each step's `anchor` is a literal `data-tour` that appears exactly once in `file`;
`tourAnchors.test.js` loads every registered tour and fails by tour and step name.

`assembleRegistry` refuses, naming the tour: a missing or extra field, a wrongly typed field, a
`start` outside `/journal/notebook`, and a duplicate id within or across tracks (including the
base id).

### 1.3 A tour starts at its own screen

Plan 4.2: a tour starts "at the screen where a member would naturally first meet it". W14-D found
the engine closed a tour opened from Help at once when its starting anchor was not on screen: it
looked once, the moment the content loaded, while the Notebook was still loading. Now:

* an entry may declare `start` (a path under `/journal/notebook`, where the engine is mounted);
  Help's Replay links to `startPath(t)`, which is that start or the Notebook root, so the base
  tour's link is unchanged;
* if the first step's anchor is not on screen and the member is not at `start` (`atStart`: same
  path and every query parameter the start names), the engine navigates there once;
* it then waits up to `START_WAIT_MS` (8 s, polled every 100 ms) for the first step's anchor and
  opens at step one. When the wait runs out it opens on whatever steps are on screen, or closes
  with nothing recorded.

### 1.4 Per-tour seen state, and why there is no new onboarding route

Plan 4.3's mechanism is one preference blob per member extending `notebook_tour` into a per-tour
record. That is `notebook_tours`, written through the existing `POST /api/auth/preferences` via
`setPrefMerged` (read-modify-write over the freshest cache, R8). The base tour keeps its own
`notebook_tour` key untouched (moving an armed capability's stored state would be a live change).

The endpoint had no `_PREFERENCE_KEYS` row for `notebook_tours` and would have answered 400 to
every save (found by W14-D; the 9/26 `notebook_daily_template` class). Row added in `e11c59167a`.

No route was added to `api/routers/notebook_onboarding.py`. The plan's lane table gives
"per-tour seen state" in that router to W14-C, and today nothing would call one: the registry has
no tour beyond the base one, so a server route now would be built, tested and unreachable. What
W14-C should weigh: `setPrefMerged` merges against THIS tab's cache, so two tabs writing different
tours' rows in the same moment can still lose one row. A server-side merge route would close that;
it becomes worth having when W14-C's "offer once" trigger can start tours on its own.
