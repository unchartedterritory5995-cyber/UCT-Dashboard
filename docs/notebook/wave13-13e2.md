## 2. The bell — one in-app line a day for a new fill

Lines 35-37 and 605 of `note_tasks.py` are the plan's own citation for the idiom: `run_task_reminders`'s claim-then-deliver pattern (an atomic `INSERT OR IGNORE` on a per-day key is the claim; a delivery that raises releases it) and `_deliver_in_app`'s one channel (`api.services.alerts.add_alert`, severity `info`, never email). The bell reuses that IDIOM, not that TABLE — `note_tasks.py` is not in this lane's file ownership, and the reminder it already dedupes (open tasks due) is a different event from a new fill.

* **The claim.** `j2_entry_context_bell_log(user_id, day)`, primary key, self-ensured in the same `_DDL` tuple `j2_entry_context` uses. `notify_new_fill(user_id, day, deliver=None)` inserts; `rowcount == 0` (another freeze already claimed today) returns without delivering.
* **The fire.** `capture_at_entry` calls it exactly when ITS OWN freeze was fresh (`out["frozen"]`, never `"already_frozen"`). `backfill_open_positions` calls `freeze()` directly — never `capture_at_entry` — so an older open position's catch-up never rings it, by construction, not by a flag check.
* **The release.** A `deliver` that raises releases the claim (`DELETE ... WHERE user_id = ? AND day = ?`) so a LATER freeze the same day retries that member instead of losing the day's bell outright.
* **Never fails the capture.** Both the inner (`deliver`) and outer (`_Conn`/store) exception handlers return `False` rather than raise; a bell failure can never fail the freeze that triggered it.
* **The member sees it** via the existing `AlertBell` (mounted in `MobileNav`, ≤1024px — the desktop `NavBar` carries no `AlertBell` today, per its own restore-note comment at `NavBar.jsx:225`; the walk's bell check therefore reads a touch-width context, not a desktop one).

## 5. A real bug the walk found, that no unit test reached

`WhyPrompt` flips its local `editing` state to `false` the instant a save's PUT resolves — one
render BEFORE the parent's own refetch (`onSaved` → `retry()`) lands a non-null `context.why`.
The saved-view branch read `why.text` unconditionally, so a member's very FIRST "why did you take
it" note crashed the component for that render. Neither existing unit test reached it: the
"already has a why" test never starts null, and the "null why" test never reaches a successful
save. Fixed to fall back to the just-typed `text` (`why?.text ?? text`) so the member sees their
own words with no gap, resolving to the server's text once the refetch arrives; a regression test
(`WhyPrompt.test.jsx`: "a FIRST save (why starts null) renders the just-typed text, never
crashes") was added. Commit `95af47aece`.
