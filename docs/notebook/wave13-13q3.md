## 2. Item 1 — Q1: `bring_to_front()` is necessary, but 13Q-2's diagnosis was incomplete

13Q-2 diagnosed the right MECHANISM (a background page ignores script-triggered
`.focus()`) and recommended `pg.bring_to_front()` immediately after `pg = ctx.new_page()`
in `run_one`. That line is added (`tools/notebook_w13q_clicks.py::run_one`) — but a full
re-run with only that change still measured Q1 keys at 99/38 (`docs/notebook/evidence/
wave13-13q3/run-remeasure/clicks.json`, committed before this was investigated further —
R-RAW), essentially unchanged from 13Q-2's own 97/36.

**Deeper diagnosis** (`docs/notebook/evidence/wave13-13q3/q1-second-attempt-diagnosis/`,
four scripts + `RESULT.txt`, all against the real sandbox, never a reimplementation):
`bring_to_front()` does make the page genuinely foreground (`document.hasFocus()===true`,
`visibilityState==='visible'`, both measured) — but a **freshly-mounted editor's FIRST
script-triggered `.focus()` call still silently fails** even on a genuinely foreground
page in this harness. A **second** attempt, on the same editor instance, succeeds.
Measured both ways: without `bring_to_front()`, two attempts still fail; with it, one
extra attempt succeeds. Neither alone is sufficient — this is NOT what 13Q-2's own
successful repro proved (their script happened to make two attempts, an artifact of its
own debugging shape, not something their write-up called out as load-bearing).

Four BrowserContext/input-method combinations were tested to rule out confounds (new
context vs. reused, click-created vs. Ctrl+K-created) — none of those explain it; only
"was a focus attempt already made on this editor instance" does.

**Fix** (`tools/notebook_w13q_clicks.py::focus_editor_body`): when the product's own
automatic attempt doesn't land, try Playwright's own `.focus()` method once — never a
product-internals reach-in (it's the same tool-level API `bring_to_front()` already is),
never counted as a step — purely to tell apart the **known harness artifact** (member
pays nothing; a real member's tab never has a "first attempt" to retry, and 13Q-2 already
proved their single attempt succeeds via jsdom + a direct real-browser check) from a
**genuine reachability defect** (the real, expensive Tab walk still runs below and is
measured honestly — the fallback is never skipped). Mutation-proved: removing the
compensation call reds `test_focus_editor_body_keys_compensation_skips_the_real_tab_walk_when_it_resolves`
specifically; a non-vacuity control (`test_focus_editor_body_keys_falls_back_to_the_real_tab_walk_when_compensation_does_not_help`)
proves a genuine defect still falls through to the real walk, using the pre-existing
`FakePage` whose `.focus()` is an inert no-op.

## 3. Item 2 — skip links

### 3a. What was added

- **`NoteEditorPage.jsx`**: a second skip link, **"Skip to editor toolbar"**, landing on a
  hidden heading at the very top of the sticky chrome (before `<header>`) — reaches the
  Ask toggle, Export (inside "More note actions") and Insert widget, all of which sit
  **above** the title in DOM order, so the existing "Skip to note" (which lands on the
  title) cannot reach them. Same H14-safe CSS recipe as the shell's own skip link
  (invisible/pointer-transparent unless focused).
- **`FolderSidebar.jsx`**: **"Skip to folder navigation"**, landing at the top of the
  sidebar. "All notes" (Q2, Q11) and "Search notes" (Q4) live in the sidebar, which
  renders **before** `#notebook-pane` in DOM — the existing "Skip to notes list" cannot
  reach them either (it lands AFTER the sidebar).
- **Instrument**: a new `use_skip_link(m, label_regex, log_label)` helper (keys mode
  only; mouse/taps never call it — nothing to skip with a pointer). Wired into
  `go_all_notes` (folder-nav skip) and into Q2, Q4, Q9, Q11, Q12, Q15, Q20 at the points
  where a skip link's landing spot is closer to the flow's target than a cold Tab walk
  from wherever focus currently sits.

### 3b. Counting decision, with evidence

A real keyboard member, seeing a visible "Skip to X" link, uses it rather than tabbing
past 20+ nav links — so the instrument now does too, and counts it the same way `press()`
already counts any keys-mode activation: the real Tab presses to reach the link (via
`tab_to_locator`, unchanged machinery) + one `Enter`. Nothing is invented; a row still
only PASSes on a path the member actually has available, and a row that doesn't improve
says so honestly below rather than being massaged into a pass.

## 5. Item 4 — Q20(b): the Insert-widget dialog never moved focus into itself

Diagnosed with a real-browser probe (`docs/notebook/evidence/wave13-13q3/
q20-dialog-diagnosis/`, full write-up in its `RESULT.txt`): `WidgetPalette.jsx` never
moved focus into the dialog on open (only once a type was picked, into the ticker
field). At 1200px this was invisible because a plain forward Tab from "Insert widget"
happened to land on the dialog's own Close button next (cost: 2, to reach "Chart"). At
390px, the SAME forward Tab instead lands backward on the "Format" toggle — the toolbar's
`.formatRun` spans toggle `display:none → display:contents` at runtime there (never at
1200px, where they are `display:contents` from first paint), and a real Tab from a
control that was JUST revealed this way does not reliably advance into the dialog —
confirmed by a direct `querySelectorAll` dump proving DOM order is identical at both
widths, so the browser's natural tab order, not markup, is what differs.

**Fix**: `WidgetPalette.jsx` now focuses the first type button (today, "Chart") the
moment the dialog opens, and refocuses it on "Back" from the ticker form — removing the
dependency on natural tab order at every width, not only the one where it happened to
work. (Do NOT edit `WidgetEmbedView.jsx`/`widgetEmbedNode.jsx` — followed; this is
`WidgetPalette.jsx` only, the dialog's own file.)

## 6. Item 5 — Q6/Q13: an instrument bug, not a product defect

**Finding, with full byte-level evidence** (`docs/notebook/evidence/wave13-13q3/
q6-q13-instrument-fix/RESULT.txt`): `tools/notebook_w13q_clicks.py::_trade_row`'s `alt`
locator was committed as `has_text=re.compile(rf"\b{sym}\b")` — but the actual bytes in
the file, confirmed via `git cat-file blob` (pre-existing, from 13Q-1's own commit
`f75f2d8f1b`, not introduced here and not a transcription artifact of reading it now),
were two literal **backspace control characters (0x08)** around `{sym}`, not the two
characters backslash+`b`. A regex of `"<backspace>CRWD<backspace>"` can never match
ordinary page text. At 1200px this was invisible because `row` (a real `<tr>`) always
matched first; at 390px the Trades surface renders `TradeCard` **buttons**, never
`<tr>` — `alt` was the only path, and it was permanently dead. This is **the instrument's
locator**, confirmed by directly probing the real function against a real sandbox and
comparing it to a byte-clean copy of the identical logic typed fresh (which found the
card instantly) — not a journal-2-0 product defect, and no journal-2-0 file was touched.

**Fix**: `has_text=sym` — the plain string, the same substring semantics `row`'s own
`has_text` already uses — never a regex, so there is no backslash-escape sequence left
in the file for a future transcription to corrupt the same way again. The now-unused
`import re` was removed with it.

| flow/mode/width | before | after |
|---|---|---|
| Q6 keys@1200 | 146–148 OVER (flaky positive — sometimes found at this width even pre-fix) | 148 OVER (consistently found now) |
| Q6 keys@390 | **INCONCLUSIVE** "not visible" | **64 OVER** (real measurement) |
| Q6 taps@390 | **INCONCLUSIVE** "not visible" | **5 OVER** (real measurement) |
| Q6 mouse@1200 | INCONCLUSIVE (no Save door on the view) | unchanged — a separate, pre-existing finding, out of scope |
| Q13 keys@1200 | 666 OVER, cap reached | 666 OVER, cap reached (unchanged — the row WAS found via `<tr>` even pre-fix; capped reaching it is a chrome-depth finding, not this bug) |
| Q13 keys@390 | **INCONCLUSIVE** "not visible" | **634 OVER**, cap reached (real measurement) |
| Q13 taps@390 | **INCONCLUSIVE** "not visible" | **3 OVER** (real measurement) |

Mutation-proved: reintroducing `re.compile(sym)` (any regex, not only the exact
backspace form) reds `test_trade_row_alt_query_is_a_plain_string_never_a_compiled_pattern`
specifically — the regression guard checks the TYPE of what Playwright actually
received, not just behaviour, which is exactly how the original bug survived review
(it looked identical to a human and to this file's own earlier Read-tool renderings).
