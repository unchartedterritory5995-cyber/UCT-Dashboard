## 1. What this lane actually found, in one paragraph

Every OVER row this lane investigated (Q2, Q4, Q7, Q9, Q11, Q12, Q15, Q20 in keys mode)
traces to the **same mechanism**: the shared app chrome — `NavBar.jsx`'s ~19-23 links
plus the Journal's own top-level tab bar (Today/Trades/Calendar/Notebook/Insights/
Compass) — sits in DOM order **before** every Notebook/Journal/Screener control a member
is trying to reach, is **not** compacted with roving tabindex, and the 13Q-1 instrument's
keys-mode model tabs **forward only** (never Shift+Tab, never activates a skip link).
Reaching a control positioned "behind" the member's current focus (inside an open note's
body, deep in the All Notes list, deep in a 30-row screener result set) therefore costs a
full wrap through 20-340+ individually-tabbable chrome/content elements — a cost that
belongs to shared, non-Notebook infrastructure, not to any file this lane may safely edit.
Section 4 below is the evidence for this, row by row, with raw trails committed.

One row (Q1) had a **different, Notebook-scoped, genuinely fixable** cause (missing focus
management) and is fixed in this lane — see section 2. Two rows (Q6/Q13) are a **real
Journal-surface keyboard/touch reachability defect at 390px**, diagnosed per the task's
explicit ask but not fixed (Journal's Trades surface, out of this lane's fix list) — section 5.

## 2. Q1 — FIXED: "new blank note, cursor in body"

**Cause:** `NotebookTab.jsx::openNote` always set `openFocus: 'title'` for a freshly made
note (the I-1 rule: "the one open whose next act is typing its title"). For a genuinely
**blank** note (no title, no template) there is nothing in the title worth a look first —
the member's next act is writing, and the instrument's own budget says so ("cursor in
body"). The extra 1 click (mouse/taps) / 4 real Tab presses (keys) was the cost of
reaching the body by hand afterward.

**Fix (3 files):**
- `app/src/pages/journal-2-0/tabs/NotebookTab.jsx` — `createNote` now computes
  `blank = !title && !bodyJson` (true only for the bare "+ New note" / palette "New Note" /
  `?new=blank` deep-link path — a template or a typed title is never blank) and passes it
  through `openNote(..., { fresh: true, blank })`. `openNote` sets
  `to: fresh ? (blank ? 'body' : 'title') : 'landmark'`.
- `app/src/pages/journal-2-0/components/notebook/NoteEditorPage.jsx` — a **second**,
  separate `useLayoutEffect` (not folded into the existing title/landmark effect) handles
  `openFocus === 'body'`: `editor.commands.focus('end')`. It is separate because the
  title/landmark targets are plain DOM refs ready on the first render `openFocus` is set,
  while the TipTap `editor` instance is async and can still be `null` on that render — a
  shared effect/dependency array would bail out once and never retry. `editorProps.attributes`
  gained an explicit `tabindex: '0'` on the ProseMirror root (a no-op for a real browser's
  tab order — contenteditable is already focusable and already in it — but load-bearing for
  `editor.commands.focus()` to be observable in jsdom/`focusableWithin`-style selectors).

**Tests (both green, mutation-proved):**
- `app/src/pages/journal-2-0/tabs/NotebookTab.test.jsx` — 5 new cases: the bare button and
  the `?new=blank` deep link assert `openFocus="body"`; a template pick, a "Blank note"
  card (title present, no bodyJson — a real discriminator case, not vacuous), and a

## 3. Instrument finding: a background-page gap, specific to programmatic `.focus()`

`tools/notebook_w13q_clicks.py::run_one` creates a **brand-new browser context and page
for every single row** (`ctx = br.new_context(...)`, `pg = ctx.new_page()`) and never calls
`page.bring_to_front()`. Chromium — correctly, by design, so a background tab cannot steal
keyboard focus from the tab a person is actually looking at — silently ignores a
script-triggered `element.focus()` call on a page that has not been brought to the front.
Playwright's **synthetic** clicks/taps/keypresses (CDP-level input dispatch, which is what
every other row in this whole program measures) are unaffected by foreground state, which
is exactly why Tab-based navigation measures correctly everywhere else in this instrument
while a programmatic focus call cannot be observed at all.

**This was measured, not guessed**, with a throwaway script reusing the instrument's own
`notebook_perf_harness.Sandbox` boot and `h._provision` member setup (never
`tools/notebook_w13q_clicks.py` itself — that file is 13Q's, not edited here):
`docs/notebook/evidence/wave13-13q2/q1-focus-foreground-diagnosis/debug_q1_focus.py` +
`RESULT.txt`. Key finding: a **manual** `editor.commands.focus('end')`, called directly via
`page.evaluate` (bypassing React, the fix, and all three timing strategies I tried), left
`document.activeElement` on `BODY` — then **succeeded** the moment `page.bring_to_front()`
was called first, with `document.hasFocus()` reading `true` throughout (ruling out the more
common "the browser window itself isn't OS-focused" explanation).

Three implementation strategies were tried and ruled out **before** finding the real cause,
specifically to make sure this wasn't a React-timing bug in the fix itself:
1. plain `useEffect` (first attempt) — `after-q1-run1`;
2. a double-`requestAnimationFrame`-delayed `useEffect`, matching `AskPanel.jsx`'s own
   documented fix for a *different* race ("Sheet claims focus... on the frame after it
   mounts... focusing on the same frame loses the race") — `after-q1-run2`;
3. `useLayoutEffect` (synchronous, before paint — the earliest point React offers) —
   `after-q1-run3`, the version shipped.

All three produced near-identical measured counts (~97/36 for keys, 3/3 for mouse/taps),
which is itself evidence the cause was never timing: nothing about React's effect
scheduling can explain three different schedules landing on the same number.

**This is not a product defect.** A real member's browser tab is, by construction, the
foreground tab they are looking at — `editor.commands.focus('end')` works for them exactly
as it works here once brought to the front. There is no DOM API a web page can call to ask
a background page to become the browser's foreground tab; only the thing automating the
browser can do that. **Recommended instrument fix, for the 13Q-owning lane (not made
here):** add `pg.bring_to_front()` immediately after `pg = ctx.new_page()` in `run_one`.
Until that lands, Q1's keys-mode numbers on this instrument will read as 36-97 regardless
of how correct the focus-management fix is — the jsdom + real-browser-manual evidence in
section 2 is what actually verifies the fix.

### 4b. Three Notebook-scoped fixes considered and rejected (with evidence)

**1. Keyboard shortcuts bypassing Tab entirely** (e.g. a chord to open Ask, or jump to the
bulk-action bar). Rejected because it **cannot move the measured score on this instrument**:
`Meter.press()` in keys mode always drives via `tab_to_locator(specific_element)` — it has
no notion of a shortcut and will keep tabbing to find the named locator regardless of what
else exists. A shortcut is real value for an actual member (who would use it instead of
Tab-hunting) but is invisible to the thing this lane's finish line asks to re-measure, so
it was not implemented here — flagged in section 6 as a real, separately-valuable follow-up.

**2. DOM reordering, relying on the chrome already being `position: sticky`** — move
`NoteEditorPage`'s sticky header+toolbar (`.chrome`, `chromeRef`) or `BulkActionBar`
(already `position: sticky; top: 0`, confirmed in `BulkActionBar.module.css:5-6`) to render
**after** the body/grid in JSX, since a sticky element's stuck position does not depend on
sibling order. **Rejected on the CSS mechanics, before touching any file**: `position:
sticky` only "sticks" once scrolled past its own natural flow position — moving an
element's JSX position changes where it sits when NOT yet stuck. Moving the header/bulk-bar
later in DOM would make it render **below the fold** (after the whole note / whole note
list) until a member scrolled past everything beneath it first — trading a measured-Tab
regression for a real, member-visible layout break. Not implemented.

**3. A page-wide focus trap** (`useFocusTrap` — the same primitive `AskPanel.jsx` and
`NoteMoreMenu.jsx` already use for their own small popovers — applied to the whole
`NotebookTab` wrap, so Tab would cycle within Notebook's own ~40-70 elements instead of
escaping to the chrome). Prototyped in analysis, not implemented, for two compounding
reasons: (a) `useFocusTrap`'s `focusableWithin` selector keys on `[tabindex]`/native
interactive tags and does **not** match a bare `contenteditable` region with no `tabindex`
attribute (the exact gap found and fixed locally for Q1 in section 2) — without the SAME
`tabindex="0"` fix the trap would not even recognise the editor body as part of its own
container; and (b) composing a new outer trap with the two **existing, tested** inner traps
(AskPanel's own `useFocusTrap`, NoteMoreMenu's `useDisclosureFocus`) needs a `shouldTrap`
gate excluding `[role="dialog"], [data-contained-disclosure], [data-sheet-panel]` to avoid
silently reintroducing the exact regression those traps were built to prevent (documented
in-file: "Lane 10E-2's keyboard walk tabbed straight out of it into the editor's toolbar").
That composition is reasoned through and appears safe on paper (the gate reads
`document.activeElement` **before** either trap moves focus, so listener registration
order cannot matter — see the reasoning trail, not reproduced here for length), but
verifying it holds across split-view (two open notes, two editors, one wrap) and against
all ~50 of `NoteEditorPage`'s own existing keyboard-contract tests needs a verification
pass broader than this lane's remaining budget allowed. **Not implemented; flagged as the
most promising Notebook-scoped candidate for a follow-up lane**, not shared chrome.

### 4c. The actual recommended fix (hand-off — not Notebook's file to change)

Convert `NavBar.jsx`'s primary `<nav>` list (`NAV_ITEMS`, ~19 links) and the Journal's own
top-level tab bar (Today/Trades/Calendar/Notebook/Insights/Compass) to **roving tabindex**:
one tab stop into the group, Arrow keys move within it, Home/End jump to the ends — the
standard pattern for a primary navigation list with this many items (this is the
"roving tabindex" cause the controlling brief itself named as a likely category). This is
a **shared, app-wide file outside this lane's ownership**, not named in the wave-13 file
ownership table, and changing it carries its own cross-page a11y verification obligations
(it is read by every single route in the product) — explicitly a controller decision, not
a unilateral Notebook-lane change. It would cut roughly 20-30 tab stops off **every one**
of Q2, Q4, Q7, Q9, Q11, Q12, Q15 and Q20 simultaneously; it is unlikely to bring the larger
ones (Q11, Q20's 390 leg, Q7) fully under budget alone, but would be the single highest-
leverage fix available and should land before anything else in this family is attempted.

## 5. Q6 / Q13 — diagnosed: a REAL Journal-surface defect at 390px, not an instrument gap

**Which:** a real, reproducible Journal-side reachability defect specific to **390px
(phone) width**, not an instrument locator gap. Fresh evidence, re-measured on the current
tree (`docs/notebook/evidence/wave13-13q2/q6-q13-diagnosis-run1/`):

| flow/mode/width | result |
|---|---|
| Q6 mouse@1200 | INCONCLUSIVE — row opens, no "Save to Notebook" door found on the view |
| Q6 keys@1200 | **OVER, 146/6** — the row WAS found and opened this run |
| Q6 keys@390 | INCONCLUSIVE — "the seeded CRWD trade row is not visible on the Trades surface" |
| Q6 taps@390 | INCONCLUSIVE — same |
| Q13 mouse@1200 | OVER, 3/2 |
| Q13 keys@1200 | **OVER, cap reached** — the row WAS found (per 13Q-1's own reading) but 600 Tab presses never reached it |
| Q13 keys@390 | INCONCLUSIVE — "the planned NVDA trade row is not visible on the Trades surface" |
| Q13 taps@390 | INCONCLUSIVE — same |

**Reasoning:** `_trade_row()` (`tools/notebook_w13q_clicks.py`) is a pure DOM query —
`pg.locator("tr", has_text=sym)` falling back to `a, button, [role=button], [role=row],
li` — with **no mode-specific or width-specific branching**. At 1200px the row is found
(by mouse in both the original and this run; by keys in this run, though not in the
original — a flaky positive, not a flaky negative, which matters: the locator can succeed
at this width). At **390px the row is never found, in either the original run or this
one, across both keys and taps modes** — the one width/outcome combination that never
once varies. A locator that is sometimes-unreliable-but-sometimes-works at one width and
**consistently** fails at a different width is evidence of a width-dependent product
behaviour, not of the locator being wrong (a wrong locator would fail everywhere, not
selectively at 390px).

Code read for a concrete lead (not fully chased — the task scopes this as diagnosis):
`app/src/pages/journal-2-0/components/TradesTable.jsx` renders a real `<table>`/`<tr>` at
desktop widths and switches to `TradeCard` (`<button data-testid="trade-card">`, genuinely
keyboard-accessible, `useIsPhone()`-gated) under 640px — so the **component itself** is not
obviously unreachable on phone. The next session should check, in order: (1) whether the
phone layout paginates or orders `allClosed` differently than desktop (`TradeJournalTab.jsx`
describes "the paginated set" — if page size or default sort differs by viewport, a
just-seeded trade could land off the first page on phone and still be present at 1200px);
(2) whether reaching the Trades tab's "Closed" segment requires an additional phone-only
step (a collapsed filter sheet, a `MoreSheet` detour) that the instrument's `q6_link_trade`/
`q13_plan_grade` flows do not perform. Not fixed in this lane (Journal's Trades surface is
not on 13Q-2's fix list, and the task's own instruction here is diagnosis).
