## Two bugs in the P3 flip tool — built, self-checked, and never run

`tools/q1_p3_guard_flip.py` is the lever P3 depends on. Both bugs would have
fired the first time it was used.

**1. `SKIPPED` was not enumerated as terminal.** It appears in **3 of the last 40
`web` deploy records**. The row never transitions, so the poller would have spun
the full 900 s budget and reported *"no new deploy record"* — which reads as a
Railway problem. What `SKIPPED` actually means is that **the process never
restarted and the old value is still live**, the precise service/process split
the tool exists to refuse to guess at.

⭐ Another workstream found the same class the same day in `pre_push_guard.py`
(`3b60707a9`, `4c2d09b1a`) — *"the row will never transition to
SUCCESS/FAILED/CRASHED"*. Independent corroboration, two tools, one day.

**2. Worse — `wait_for_own_deploy` took the first NEW record, not OUR record.**
Its docstring says *"identified by ID, not by position"*, and it was — but *"a
row that did not exist before I started"* is a **timestamp, not an identity**. A
concurrent push supplies one (three sessions landed inside one hour on
2026-09-17, which is why the by-ID rule exists at all), so the flip could have
reported **SUCCESS on somebody else's deploy**.

Identity is now the **commit**: `--set` redeploys the commit already running, so
ours carries `base_commit` and a foreign build does not. It fails loud rather
than falling back to the newest new row.

⚠️ **My first rail for this was vacuous.** It asserted the token `base_commit`,
which also appears in the signature and the timeout message — so replacing the
guard with `if False:` left the rail **green**. Caught by the mutation proof,
which is the only thing that could have caught it. It now asserts the comparison
(`commit != base_commit`). Four mutations, all RED, restore GREEN.

## The runner clobbered queue edits made during a run

`save_queue` wrote back a snapshot taken up to 55 minutes earlier, so anything
staged while a cell ran was silently reverted.

**Found by causing it, and it fired:** the P3 cell staged mid-run was reverted
and had to be re-applied. The failure is silent — the run still reports its own
result correctly — and the cost lands on the **next** window as *"nothing
staged"*, which is the exact failure this queue exists to prevent, arriving
through the tool that prevents it.

`save_entry()` now merges only the entry the runner owns onto the **current**
file. Proven with a before/after: the merge keeps a concurrently-staged cell, the
old path loses it.

derived from the **measured** 87 s/cell plus one 360 s swap-wait. The unit of

asking the second-writer question: fewer cells to run, a fuller-looking table,
and the measurement never taken. ⭐ The tell was arithmetic — the banked

**Also split:** one queue cell described two runs with **opposite** expected
verdicts (`expect: DEFERRED-BY-GUARD` beside `held_why: "…flipped to
unknown-only"`). Each reading is the other's failure condition, so `expect` would
have endorsed the wrong answer whichever way it ran. Now W2 (guard full) and P3
(guard narrowed), each naming its own required flag state.
