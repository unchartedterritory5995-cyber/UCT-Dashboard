## 2. The mechanism, and the role-pattern decision

Each group's container (`NavBar.jsx`'s `<nav>`, `JournalLayout.jsx`'s desktop `<nav>`,
`JournalMobileNav.jsx`'s `<nav>`) now carries exactly **one** reachable item at a time
(`tabIndex=0`); every other item in the same group carries `tabIndex=-1`. Arrow keys move focus
**and** the roving stop among the group's own items (`ArrowUp`/`ArrowDown` for NavBar, a vertical
rail; `ArrowLeft`/`ArrowRight` for the Journal's horizontal tab row), with `Home`/`End` jumping to
the first/last item and wraparound at the ends. A disabled item (the unpaid Compass teaser, a real
`<button disabled>`) is skipped by the arrow-key stepper, since `.focus()` on it is a no-op anyway.

**Role decision:** the task's brief named either the WAI-ARIA tabs pattern or the toolbar pattern,
"whichever matches its current role semantics." The existing items are plain links (`NavLink`/
`Link`, native `<a>`) and, for one locked teaser, a native `<button>` — not `role="tab"` — and the
containers are genuine landmark `<nav>`s (NavBar.jsx is the app's primary navigation landmark;
`aria-label="Journal sections"` names the Journal's). The tabs pattern would require relabelling
every item `role="tab"` inside a `role="tablist"`, which the brief's "keep its existing roles/
names" rules out. The toolbar pattern's defining container role, `role="toolbar"`, was **not**
added either: overriding `<nav>`'s implicit `role="navigation"` would remove the page's primary
navigation landmark for screen-reader users doing landmark navigation, which is a real regression
the brief did not ask for and the concrete, testable asks (one Tab stop, Arrow/Home/End move
focus, Enter still activates, focus lands on the active item) do not need. What shipped is the
**roving-tabindex keyboard mechanics common to both patterns**, with every existing role, name,
label, route and visible order left exactly as it was. `aria-current="page"` — which
react-router's own `NavLink` already sets on the active route — is read, not duplicated by a new
attribute, to decide which item starts (and stays, until the member moves focus inside the group
themselves) as the roving stop.

searched for every occurrence of a NAV_ITEMS label or a PRIMARY_NAV label as a **named trail

|---|---|---|---|

| Q11 | 390 | 0 | 2 ("Notebook" twice) |
| Q4, Q9, Q12, Q15, Q20 | both | 0 | 0 |

**A single occurrence is exactly what the fix predicts**: pre-fix, a forward Tab walk that passed
through NavBar's rail would have logged up to 19 separate named presses (`UCT Terminal`, `Charts`,
… `Support`); post-fix it logs exactly one (whichever item is the roving stop — here, `Journal`,
the nav item matching the current route's top-level segment). The same holds for the Journal's own
6-item bar collapsing to one `Notebook` entry. The rows with **zero** occurrences (Q4, Q9, Q12,
Q15, Q20) are exactly the ones whose own skip-link-based path (`use_skip_link`, 13Q-3) never
revisits chrome at all — those rows' unchanged numbers are not a measurement gap, they are the
correct, confirmed outcome of a flow that never walks through NavBar or the Journal tab bar in
the first place. Q2 and Q11's forward Tab searches, by contrast, each wrap around the full
document at least once (through the community-chat widget, `BODY`, the skip links, and back into
the chrome) before finding their target — which is where the 1–2 occurrences, and the bulk of the
measured improvement, come from. (Full per-step trails: `clicks.json` → `rows[]` where
`flow in {"Q2","Q7","Q11"}` and `mode=="keys"` → `steps[].trail`.)
