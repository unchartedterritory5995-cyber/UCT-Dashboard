## 1. What this lane found and fixed, in one paragraph each

> Correction, 2026-10-06 (lane FIN-A11Y, `docs/notebook/fin-a11y.md`, finding I-5): from the search
> box only **ArrowUp and ArrowDown** move the virtual target now. Left, Right, Home and End were
> taking the text caret's keys, so a member could not edit what they had typed. Type-to-search and
> Enter-to-pick below are unchanged.

**Q2** ("new note from a template with a ticker"): 13Q-1/13Q-2/13Q-3 all measured the
Templates dialog's own card list costing 23+ real Tab presses to reach one named card by
Tab alone — the dialog had arrow-key navigation between cards already (wave 10), but no
way to *reach* a card without walking every one first. This lane gave the search box
real keyboard entry: it autofocuses when the dialog opens (`autoFocusSearch`, the same
`autoFocus` convention `Sheet.jsx` already special-cases for a dozen other dialogs), and
while it holds focus, Arrow/Home/End move a virtual "active card" target and Enter clicks
it — reusing the card's own existing `onClick`, never a second `onPick` path. Typing a
template's name (or any word in its own search index) narrows to it, same filtering the
dialog already had. Measured: the dialog's own card-reach segment goes from ~23 real Tabs
to a type (not counted) + one Enter.

**Q11** ("tag and move 5 notes"): the bulk-action bar sits near the top of the notes
pane, but a member mid-selection has focus wherever their last Space landed — reaching
"Tags" or "Move to select" from there costs a full forward Tab-walk past however many
notes remain in the view (measured 167–527 real presses across prior lanes' runs).
This lane added a documented keyboard shortcut (**Ctrl+Alt+B**, same chord convention as
the existing Ctrl+Alt+D "Today" shortcut) that jumps focus straight into the bar, plus a
**visible hint** on the bar itself naming it (so a sighted member sees it without needing
focus there first — the bar is `position: sticky`, so it's on screen the instant a
selection exists). The bar's own action buttons (Tags, Favorite, Unfavorite, Export,
Archive, Trash — plus Move once a folder is chosen) now form **one roving group**:
Left/Right/Up/Down move the single Tab stop among them. Selection itself got cheaper too:
**Shift+ArrowDown/ArrowUp** extends the selection to the adjacent note and carries focus
with it (Space alone already ticked the focused row cheaply; this cuts repeated
selections to one keystroke each, no Tab).

**A real measured wrong turn, found and fixed before this lane's own re-measurement
finished (kept here deliberately — it is evidence the fix works, not just a claim):** the
shortcut's first implementation landed on the roving group's own *active* button, which
is "Tags" by default (Move starts disabled). That works for the *first* reach. But after
tagging, a *second* press of the shortcut landed on Tags again — and "Move to select"
sits **before** Tags in the bar's own DOM order, so a forward Tab-hunt from Tags can never
reach it; it wraps the **entire page** back around. Measured: **145 real presses**
(`docs/notebook/evidence/wave13-13q5/run-1/clicks.json`, `Q11/keys/1200`, step 23). The
fix: the shortcut always lands on the bar's own **stable first control** (the Move
`<select>`, where one exists) rather than whichever button is roving-active — every other
control in the bar sits *after* it, so it is cheap to reach from there regardless of which
control was used last. Re-measured after the fix: that same reach is **0 real Tabs**
(`run-2-final/clicks.json`, step 23) — direct hit, both times.

## 2. Q2 — the Templates dialog's own search box

### 2a. What was added

`app/src/pages/journal-2-0/components/notebook/TemplatePicker.jsx`:
- **`autoFocusSearch` prop** (default `false`) — passed `true` only at the Sheet-wrapped
  "New note" dialog call site in `NotebookTab.jsx`; the inline empty-notebook mount
  (no dialog) does not pass it, so landing on an empty notebook for the first time never
  steals focus from wherever the page load put it. Implemented as the native HTML
  `autoFocus` attribute on the `<input type="search">` — the exact mechanism
  `Sheet.jsx`'s own focus effect already defers to (`Sheet.autoFocus.test.jsx`'s
  documented pattern, used by TickerActions/BuilderSheet/CotData/ModelBook/Watchlists/
  MobileBoardsSheet/MobileIndicatorSheet/ConnectTokenModal/SavedViewEditor/BuilderView) —
  no new focus-timing code, no re-litigating the Q1 background-page finding.
- **A virtual "active card" target**, driven entirely from the search box, real DOM focus
  never leaving the input:
  - Reset on every `query`/`category` change to the **first REAL match** — never Blank or
    the My Playbook pointer card, both tagged `data-template-anchor=""` (the one new
    markup attribute) and explicitly excluded. A query matching no real template sets the
    target to **nothing** (not Blank) — Enter on "zzzznosuchtemplate" does nothing, rather
    than silently creating a blank note (a real bug this lane's own first test run caught
    and fixed before it shipped — see §2c).
  - Arrow/Home/End from the search box move the target the same distance
    `onGalleryKeyDown` already moves real DOM focus from a card (same `MOVES` map, same
    "ends hold, never wrap" rule).
  - Enter clicks the target card via its own existing `onClick` — never a second `onPick`
    call site, so "every card hands onPick the catalog's own template object" (the
    pinned gallery rail) covers this path for free.
  - Painted via a `data-active="true"` attribute (same gold ring as `:focus-visible`),
    only while the search box itself holds real focus.
- **Nothing about the card's own click/Enter/Space contract changed.** The pinned rail
  `TemplatePicker.gallery.test.jsx`'s *"every card is in the Tab order (no roving tabindex
  hides one)"* test is untouched and still green — no `tabIndex` is ever set on a card.
  That test is why this lane did **not** implement literal roving-tabindex for the card
  grid itself (which would have hidden cards from Tab) — the task's "roving tabindex"
  language is satisfied by the *search box's* virtual target instead, which is additive:
  a member who never types still has the exact same full Tab-everywhere path as before.

### 2b. Known limitation, stated rather than hidden

The `data-active` highlight is repainted in a parent-level effect keyed on
`[activeIdx, searchFocused, q, category]`. A member template arriving from
`MemberTemplates.jsx`'s own async fetch is **that component's own state**, invisible to
this effect's dependency array — so the visual ring can lag one tick behind a member
template appearing. The keyboard **function** never lags: Enter reads the live DOM at the
moment it fires, so the correct card is always picked; only the cosmetic ring can be
briefly stale. Not chased further — narrow, cosmetic, and fixing it needs either lifting
state out of `MemberTemplates.jsx` (its own refactor) or a `MutationObserver` (new
machinery for a cosmetic gap).

### 2c. A real bug this lane found and fixed in itself before shipping

The first implementation's reset-on-filter logic fell back to index 0 (Blank) whenever no
real template matched a query — so typing a nonsense query and pressing Enter in the
search box **created a blank note**, a real defect (a phantom pick on a query the member
typed because nothing matched). Found by this lane's own new test
(`TemplatePicker.searchKeyboardReach.test.jsx`, "a query matching nothing never fires a
phantom pick") before any commit shipped it. Fixed: the reset effect now sets the target
to **-1** ("nothing") rather than falling back to 0 when no real template matches, and
Enter's handler explicitly guards `activeIdx < 0`. Verified both ways — the control test
passes, and "an empty query defaults to Blank" (the *intended* index-0 behaviour) still
passes separately.

## 3. Q11 — the bulk-action bar's jump shortcut, roving group, and cheap selection

### 3a. What was added

**`app/src/pages/journal-2-0/lib/bulkActionsShortcut.js`** (new) — `isBulkActionsShortcut`
(Ctrl+Alt+B / Cmd+Option+B, physical-key check via `e.code`, AltGr-guarded — the exact
pattern `dailyNote.js`'s `isDailyShortcut` already uses for Ctrl+Alt+D) and
`bulkActionsChordLabel()` (the platform-correct label for the visible hint).

**`app/src/pages/journal-2-0/tabs/NotebookTab.jsx`**:
- A `window` keydown effect, gated on `selection.count > 0` (same gating convention as the
  existing Esc-clears-selection effect beside it): on the shortcut, focuses the bar's
  stable anchor — `[data-bulk-move-select]` where one exists, else the first enabled
  `button`/`select` in the bar (covers Trash view's lone Restore button).
- `handleSelectionGridKeyDown`, wired to the note grid's `onKeyDown`: on
  `Shift+ArrowDown`/`Shift+ArrowUp` from a note's own checkbox, extends the selection to
  the adjacent note (`notes[at ± 1]` — `notes` is already in the grid's own visual order)
  via `selection.toggle(id, { shift: true })` — **reusing** `noteSelection.js`'s existing
  shift-range math (`applyToggle`), never a second range implementation — and moves real
  focus to the adjacent checkbox so repeated presses keep extending. A bare `ArrowDown`
  (no Shift) is an explicit no-op control, so ordinary Tab/Arrow browsing of the list is
  unaffected.

**`app/src/pages/journal-2-0/components/notebook/NoteCard.jsx`**: the checkbox gained
`data-note-select-id={note.id}` — needed because `data-note-card-id` lives on the card
`<button>`, a **sibling** of the checkbox under `.selectWrap`, never its ancestor, so
`input.closest('[data-note-card-id]')` cannot reach it from the checkbox.

**`app/src/pages/journal-2-0/components/notebook/BulkActionBar.jsx`**:
- A roving-tabindex group over the action buttons (Move, Tags, Favorite, Unfavorite,
  Export selected, Archive, Move to Trash — tagged `data-bulk-action=""`; Trash view's
  lone Restore, and Archive view's Unarchive/Export/Trash, the same pattern). One
  non-disabled button carries `tabIndex=0`; the rest `-1`. Left/Right/Up/Down (reusing the
  exact `onGalleryKeyDown` scoping convention TemplatePicker already uses — a keypress
  must originate from a `[data-bulk-action]` element) move the stop and real focus
  together; the ends hold, never wrap.
- **Deliberately still `role="group"`, never `"toolbar"`** — the existing pinned test
  (*"a toolbar promises roving arrow-key focus this bar does not have"*) is untouched and
  still passes; this lane adds the arrow-key behaviour **without** the ARIA role that
  technically pairs with it, a known, stated trade-off (§3b).
- `data-bulk-move-select=""` on the Move `<select>` — the jump shortcut's stable anchor,
  deliberately **outside** the roving group (mixing it into arrow-key navigation would
  reopen review B1: a closed `<select>`'s own native arrow-key value-changing behaviour).
  Giving it this role is not the B1 hazard — B1 was about *arrow keys on a focused
  select changing its value*; a plain `.focus()` call changes nothing.
- A visible hint, `<chord label> jumps here`, next to (not inside) the existing
  `aria-live` "N selected" span — kept separate deliberately so the pinned rail asserting
  an exact `"{count} selected"` node keeps matching.

### 3b. Known limitation, stated rather than hidden

The roving group's "active" stop is **positional**, not entity-tracked: if the Move
button transitions from disabled to enabled (a folder chosen) while a *different* button
is the active stop, Move — now first in the live list — can become the new `tabIndex=0`
stop, silently relocating where plain Tab lands next. **This does not affect the arrow
keys themselves** (they read the keydown's own real-focus target, never the stored
index), so a member already navigating with arrows is unaffected; only the *next* bare Tab
could land somewhere unexpected, recoverable in one Left/Right. Narrow — it needs a mouse
pick on the folder select mid keyboard-navigation of this exact bar — and not chased
further here; stated in-code (`BulkActionBar.jsx`) and tested
(`BulkActionBar.rovingGroup.test.jsx`, "choosing a folder enables Move and repaints its
tabIndex").
