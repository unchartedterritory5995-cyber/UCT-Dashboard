Branch `feat/notebook-w13h3`, base `9861c4d4d3` (the wave-13 landing tip, = 13H-2's close).
Picked up 13H-2's open item (`docs/notebook/wave13-13h2.md` §5, §10): with the toggle-press bug

## 1. What was measured, and what it ruled out

Before touching any code, `tools/notebook_w13h3_diag_walk.py` reproduced the bug with heavy
instrumentation: at every one of three touch taps it recorded the full native event log
(`pointerdown`/`touchstart`/`pointerup`/`touchend`/`mousedown`/`mouseup`/`click`, each with
target, `pointerType`, `isTrusted`), the bounding box of every on-page canvas tagged with a
stable per-element identity (to catch a node-view remount between taps), and — once the shape
of the bug became clear — the full ancestor chain `document.elementFromPoint(x, y)` returned at
each tap's exact coordinates (`docs/notebook/evidence/wave13-13h3/diag-run3/`).

**That chain is the finding.** At a 390px-wide embed, with "Horizontal Line" armed (confirmed,
same armed-state read 13H-2 built), the first two of three taps did not reach the canvas at
all:

```
attempt 1 (y=356.3): BUTTON._btn_18zdh_155  [a ChartToolbar tool button]
attempt 2 (y=422.3): DIV._actions_18zdh_147 [ChartToolbar's own actions row]
attempt 3 (y=488.3): CANVAS                 [the chart, at last]
```

Walking the ancestor chain named the covering element precisely:
`DIV._toolbar_18zdh_5` — `ChartToolbar.module.css`'s own `.toolbar`, `position: absolute`,
`z-index: 5` — measured at **`[x:73, y:276, w:252, h:170]`**, against a canvas measured at
**`[x:61, y:272, w:268, h:300]`**. The toolbar starts at the canvas's own top edge and is 170px
tall — **57% of the canvas's height** — because `ChartToolbar` renders its full ~20-button
desktop roster at 40px per button, unconditionally, and at a 390px-wide embed that wraps onto
three rows. A tap anywhere in that covered band hits a toolbar element, never the canvas; only
a tap below row three ever reaches it — which, for the walk's three fixed tap heights
(28%/50%/72% of the canvas), was always and only the third. That matches 13H-2's own finding
exactly ("always the last," never a timing issue — a 10s settle-wait on attempts 1–2 found
nothing, because nothing was ever sent).

**This is a pure DOM layout/z-order defect, not a touch-event-routing one — ruled out by the
same evidence.** `ChartDrawingOverlay.jsx`'s own touch-claim machinery (`claimAt`) correctly
steps aside the instant a tool is armed (`if (g.activeTool) return null // a tool is armed → the
canvas React handlers own it`), so none of its `stopPropagation` logic was ever in play for
these taps. 13H-2's `widgetEmbedStopEvent` fix (stopping a `mousedown` on
`[data-widget-embed-body]` from reaching ProseMirror's click-to-select) is also unrelated and
unaffected: every event in the log above is a real, `isTrusted` browser event landing on a real
DOM element — the chart's own React `onPointerDown` on the overlay canvas works correctly
*when a tap actually lands on the canvas*. The bug is that two of three taps never did, because
a floating UI element occupied the screen space the walk (and, for the covered price levels, a
real member's finger) was aiming at.

**Why the embed specifically, never bare `/charts`:** `ChartEmbed.jsx` always passes
`showDrawingTools={false}` to `StockChart`, so Draw mode here runs exclusively through
StockChart's `annotationsEditable` branch — the Model-Book-authoring code path, which renders
`ChartToolbar` unconditionally and has **no `MobileDrawBar` swap at all**. The swap
(`mobileDrawBar` prop → `<MobileDrawBar/>` instead of the desktop toolbar, with
`hiddenHost` collapsing `ChartToolbar`'s own visible strip) exists only on StockChart's
*other*, `showDrawingTools={true}` branch — the one bare `/charts`'s phone shell takes. That is
why the controller's independent check on `/charts` at 390 and 820px touch placed 3/3: the
*same* `ChartDrawingOverlay` was never in question, but `/charts` never puts `ChartToolbar`'s
desktop strip in front of a touch user at all.

Evidence, all raw, all committed before interpretation:
`docs/notebook/evidence/wave13-13h3/diag-run1/` (first pass: touch/pointer events are NOT
suppressed reaching the embed, ruling in the layout theory), `diag-run2/` (re-measuring the
canvas box immediately after arming the tool changes nothing — the toolbar's presence, not its
timing), `diag-run3/` (`element_from_point_chain`, the finding above), `diag-run4-after-fix/`
and `diag-run5-after-fix2/` (building and then correcting the fix itself — see §3).

## 2. Why the fix lives in the embed, not in `ChartToolbar.jsx`/`StockChart.jsx`

The architecturally complete answer is that StockChart's `annotationsEditable` branch should
get the same `mobileDrawBar` swap its `showDrawingTools` branch already has —
`ChartToolbar.jsx` even carries a ready-built `hiddenHost` prop for exactly this (`"Phone chart
shell: MobileDrawBar presents the drawing tools instead, so this strip hides ENTIRELY"`), it is
simply never passed `true` on the annotation path. That is a change to `StockChart.jsx` (which
branch renders `ChartToolbar`/`MobileDrawBar` and with what props) and arguably
`ChartToolbar.jsx` itself — both named as off-limits for this lane unless the fix cannot live
in the embed.

**It can.** The toolbar is `position: absolute`; it floats *over* the canvas rather than
displacing it in the flow. Growing the canvas's own rendered height — a purely Notebook-side
decision, made once per Draw-mode session — does not change the toolbar's size or position, but
it does change what *fraction* of the canvas the toolbar covers, turning "57% of a 300px canvas
is unreachable" into "the same ~170–260px fixed footprint against a canvas tall enough that the
covered band is a small slice near the top." This is the same idiom
`WidgetEmbedView.module.css`'s `.frame.annotating` rule already uses for **width** (forcing a
full breakout while drawing, reverting on Done) — this lane extends the same "give Draw mode
more room, revert on exit" pattern to **height**, for the one input class (coarse/touch
pointers) that actually needs it.

The `StockChart.jsx`/`ChartToolbar.jsx` swap is recorded below (§6, open items) as the
recommended follow-up, not implemented here.

## 3. The fix

`WidgetEmbedView.jsx`, gated on `annotate && useCoarsePointer() && attrs.widgetId === 'chart'`:
a `useLayoutEffect` measures the real, rendered bottom edge of the floating toolbar — every
`button[aria-label]` inside the embed's own `[data-widget-embed-body]` div whose own top sits
within `TOOLBAR_BAND_PX` (400px) of the body's top edge, i.e. the top-anchored toolbar and
nothing else. The furthest such button's bottom, minus the body's own top, is `drawClearance`;
it re-measures on width change (the toolbar's row count is a function of width, never of the
height this effect sets) and resets to 0 the instant Draw mode closes or the pointer is fine —
nothing here is persisted.

`widgetEmbedCore.js`'s new, pure `annotateEffectiveHeight(baseHeight, drawClearance)`:
`drawClearance <= 0` → unchanged; otherwise `min(EMBED_MAX_H, max(baseHeight, drawClearance +
ANNOTATE_DRAW_BUFFER_PX))` — never shrinks an already-taller (member-resized) embed, and is
clamped to the same 1400px ceiling the corner-resize handles already obey (`EMBED_MAX_H`,
moved into `widgetEmbedCore.js` so both consumers share one constant). `ANNOTATE_DRAW_BUFFER_PX
= 700`: sized so a tap in the canvas's *top third* — not just its lower two thirds — lands
clear of the toolbar; at the measured 390px case (`drawClearance ≈ 174`) that is a ~874px
canvas, large enough that even the walk's own highest tap (28% from the top) clears the 174px
toolbar with margin.

### A feedback loop, measured and killed before it shipped

The first version of the measurement effect re-ran on a `ResizeObserver` watching the embed's
own body element. Growing the body's height to add clearance fired that same observer, which
re-measured, which — because `ChartToolbar` also renders at least one control anchored near the
chart's own *bottom* (whose viewport Y necessarily grows with the body) — read a larger
`maxBottom` and grew the height again: an unbounded loop that reached **16,285px** in one run
(`docs/notebook/evidence/wave13-13h3/diag-run4-after-fix/walk.json`). Two independent fixes,
both required and both kept as named guards with their own mutation proof (§4):

1. re-measure only on a **width** change (the pre-existing outer `ResizeObserver` on the
   wrapper already tracks this) — the toolbar's row count is a function of width, never of this
   effect's own height decision;
2. only count a button whose own top sits within `TOOLBAR_BAND_PX` of the body's top — so
   bottom-anchored chrome can never be mistaken for the top-anchored floating toolbar this
   measurement exists to clear.

## 5. The walk itself needed two more fixes to prove it — same precedent as 13H-2

Re-running `tools/notebook_w13h2_walk.py` against the product fix surfaced two further
walk-side bugs, fixed in the same file, following the exact precedent 13H-2 itself set (three
walk-tool fixes alongside its own product fix, §3 of that lane's doc). All in
`draw_three_lines`:

1. **A fresh per-tap measurement, not one taken before any tool was armed.** This lane's fix
   can legitimately grow the embed TALLER than the viewport while Draw mode is open (§3) — a
   canvas box read once, early, can be stale the moment the layout grows. `draw_three_lines` now
   calls a `biggest_canvas_box()` helper fresh before every tap.
2. **Scroll the REAL scroll container, not `window`.** The first attempt at (1) also added
   `window.scrollBy(...)` when a computed tap point would land outside the viewport — and
   silently did nothing: per CLAUDE.md's own "Mobile layout gotcha," this app scrolls an inner
   `.main`-class element (`overflow-y: auto`); the document/window itself does not scroll. A tap
   dispatched at a window-relative Y past the (fixed) viewport height is delivered to `<html>`,
   never the canvas — measured directly
   (`docs/notebook/evidence/wave13-13h3/diag-run5-after-fix2/`, `target: 'HTML.'`). Fixed by
   walking up from the embed's own DOM node to the nearest ancestor that actually has overflow
   and scrolling *that*.
3. **Dispatch via raw coordinates, not a canvas `Locator`'s own `.click()`/`.tap()`.** An
   intermediate attempt targeted a specific canvas by index through a Playwright `Locator` (to
   get its built-in scroll-into-view) — and broke the **V1200 desktop** pass:
   `Locator.click`'s actionability check insists its own chosen element receives the event, and
   the chart stacks several same-sized canvases (the candle-pane canvas sits *under* the drawing
   overlay's canvas, both reporting the identical bounding box) — the locator sometimes named
   the wrong one and hung for the full 30s timeout
   (`docs/notebook/evidence/wave13-13h3/walk-h2-rerun1/`, `"<canvas> … subtree intercepts
   pointer events"`). Reverted to raw `touchscreen.tap(x, y)` / `mouse.click(x, y)`, which asks
   the BROWSER what is actually on top at that pixel — exactly what a real finger or mouse does,
   and exactly how 13H-2's own walk worked before this lane touched it.

## 8. Open items

1. **The architecturally complete fix is a `StockChart.jsx`/`ChartToolbar.jsx` change**, out of
   this lane's scope by its own brief: give the `annotationsEditable` render path (which a
   chart embed's Draw mode always uses) the same `mobileDrawBar` → `MobileDrawBar` swap the
   `showDrawingTools` path already has, so a touch member gets the labeled, 44px-tall drawing
   rail instead of a wrapped desktop toolbar at all. `ChartToolbar.jsx`'s own `hiddenHost` prop
   already exists for exactly this; it is simply never passed `true` on this path. This lane's
   height-clearance fix is a complete, working mitigation (proven 3/3 at 390px) and not a
   stand-in that must be revisited before the embed is usable — but the UX a touch member gets
   (a very tall chart during Draw mode, vs. a compact chart with a proper bottom drawer) is a
   real difference a future lane with standing to edit `StockChart.jsx` should close.
2. **`TOOLBAR_BAND_PX` (400) and `ANNOTATE_DRAW_BUFFER_PX` (700) are sized against the one
   measured case** (390px wide, ChartToolbar's current ~20-button roster). Both are generous
   past that measurement on purpose (see their own comments), but neither is re-derived from
   `ChartToolbar`'s actual button count — a future roster change that meaningfully grows the
   toolbar's wrapped height would need these re-measured, not assumed to still hold.
3. **Only verified down to 390px.** The walk runs at 1200 and 390; an even narrower real device
   (320px) was not measured directly — `TOOLBAR_BAND_PX`'s margin (§3, open item 2) is the
   lane's answer to that gap, not a direct measurement of it.
