## 1. The fix (StockChart.jsx)

StockChart.jsx's `mobileDrawBar` prop (wave 8, previously only read by the
`showDrawingTools` branch) now ALSO gates the `annotationsEditable` branch
(~line 20068): `{annotationsEditable && mobileDrawBar && <MobileDrawBar .../>}`
renders the phone drawbar (open unconditionally — the block itself is gated on
Draw mode already being on; `onClose={NOOP}` since there is no separate
open/close state to collapse to), and the annotationsEditable `ChartToolbar`
gets `hiddenHost={mobileDrawBar}`, exactly mirroring the `showDrawingTools`
branch a few hundred lines above.

`ChartEmbed.jsx` passes `mobileDrawBar` straight through into `stockChartProps`,
double-gated (`!!annotate && !!mobileDrawBar`) so a stale `true` can never light
up the swap on a read-only chart. `WidgetEmbedView.jsx` computes the value from
its own `annotate` state and the same `isCoarsePointer` read 13H-3's workaround
used.

This is the minimal, separable edit to the shared file: one new render branch
(~10 lines) and the prop's doc comment extended, touching no other StockChart
behaviour. Every existing `showDrawingTools`/`annotationsEditable` caller that
never passes `mobileDrawBar` is byte-identical to before (proved by the
no-op-on-other-caller test case and by mutation M1/M2 below).

The annotations layer has no undo/redo history (`useChartDrawings` — the source
of `undo`/`redo`/`canUndo`/`canRedo` — backs only the `showDrawingTools`
overlay), so the annotationsEditable `MobileDrawBar` call passes neither
`onUndo` nor `onRedo`. That turned out to matter a great deal — see §3.

## 2. Why this lives in StockChart.jsx and is still minimal

The brief asks this explicitly: the StockChart edit is shared code, so say so
plainly. It is:

- **One new prop read**, re-using a prop (`mobileDrawBar`) that already existed
  for a different branch — no new prop surface.
- **One new conditional render block**, scoped entirely inside
  `annotationsEditable &&`, so it cannot interact with the pre-existing
  `showDrawingTools` branch's own, separate MobileDrawBar wiring a few hundred
  lines above (different JSX subtree, different state, different gate).
- **Opt-in by construction**: `mobileDrawBar` defaults to `false`/undefined on
  every caller that does not pass it (Model Book, Setup Library, index-pane
  marks, and every other `annotationsEditable` site in the codebase), so none
  of them change behaviour. Mutation-proved (M1, M2 below): dropping either
  gate fails a test asserting the OTHER callers' behaviour is untouched.
- **The MobileDrawBar.jsx fix (§3) is the same shape**: an existing prop
  (`onUndo`/`onRedo`) now controls whether two tiles render at all, rather than
  always rendering them disabled. The `showDrawingTools` branch always passes
  both handlers, so it is byte-identical before and after (mutation M4 proves
  the guard is load-bearing; the "a caller WITH real history" test case proves
  the other branch is unaffected).

## 3. The bug this lane actually had to find: MobileDrawBar's own width squeeze

Wiring MobileDrawBar into the Notebook embed (§1) did **not** make V390 pass by
itself. Measured, in order:

**walk-2** (MobileDrawBar swap wired, 13H-3's workaround still active): V390
still failed, now on the TOOL-ARM press itself (`V390_tap_points: None` — the
failure happened before any canvas tap was attempted), with Playwright's retry
log showing the tap target intercepted alternately by `<html>`, MobileDrawBar's
own `<div role="toolbar">`, and a sibling button's icon. A genuinely new failure
mode, distinct from 13H-3's own (desktop ChartToolbar wrapping over the canvas).

**walk-3** (same code; a geometry diagnostic added to the walk right before the
tool-arm press — `tools/notebook_w13h2_walk.py`'s `V390_drawbar_geometry`,
reading `.bar`/`.tools`/`.allTools`/`.side`'s real `getBoundingClientRect()` plus
`document.elementFromPoint` at the Horizontal button's own reported center):
confirmed the mechanism directly. `.bar` is 268px wide (it matches the chart's
own canvas container, not the 390px viewport — the Notebook's note-reading
column is narrower than the full-bleed phone chart shell MobileDrawBar was
built for). MobileDrawBar's fixed, non-shrinking chrome — `.done` (54px) +
`.allTools` (44px) + `.side`'s four tiles (Eraser/Undo/Redo/Magnet, 181px) —
totals ~279px before `.tools` gets anything, which **already exceeds the
268px-wide bar**. Flexbox's result: `.tools` clamps to **0px** (`toolsClientWidth:
0`), so the ENTIRE 19-tool scrollable rail is invisible — not just the
"Horizontal" tool the walk needed, nothing in `.tools` is reachable at all —
and the layout collapses leftward: `.allTools` and `.side` render immediately
after `.done`, with `.side`'s own rightmost tile pushed ~82px past the bar's
right edge. The pixel Playwright (and a real thumb) would tap for "Horizontal"
lands on whatever is ACTUALLY painted there once `.tools` has zero width —
confirmed `elementAtHorizCenter: "svg...[object SVGAnimatedString][]"`, the
Eraser tile's own icon glyph, since `.side` now starts immediately after
`.allTools`.

This is a real, pre-existing defect CLASS in this exact component, not new to
this lane: `toolPickerRepeat.test.jsx`'s own header already documents it —
*"[repeatMode] shipped on the bar first; at 390px that left the tool rail 51px
wide — 0.98 of one tile, down from ~3 — because the side cluster is
`flex: 0 0 auto`"* — and was fixed there by moving a control OFF the bar
entirely. `ChartToolbar.jsx` independently already renders its OWN Undo/Redo
the same conditional way this lane now applies to MobileDrawBar
(`onUndo = null, onRedo = null` defaults, `{onUndo && (<button .../>)}`) —
this lane's fix is the same established idiom, not a new one.

**The fix** (`MobileDrawBar.jsx`): render the Undo and Redo tiles ONLY when a
real `onUndo`/`onRedo` handler was passed, instead of always rendering them
(permanently disabled, since `canUndo`/`canRedo` default `false`) when no
handler exists. The annotationsEditable caller has no undo history and so never
passed either handler — these were two dead, always-disabled tiles taking up
~84px for that caller specifically, while the `showDrawingTools` branch (which
DOES have real undo/redo) always passes both and is therefore unaffected.

**walk-4** (fix applied, dist rebuilt, same code otherwise): `.tools` measured
at **59px** (not 0), `.allTools`/`.side` moved back inside the bar's own right
edge, and **V390 went 3/3** — `V390-2_draw_and_assign_roles: PASS — 3 lines
placed by tap, 3 stored`. Full raw evidence:
`docs/notebook/evidence/wave13-13h4/walk-3/` (the diagnostic that found the bug)
and `walk-4/` (the clean pass).

## 4. The 13H-3 workaround: REMOVED, with evidence

Measured, not assumed, and **independent of §3's fix** — this was decided and
proved BEFORE the width-squeeze bug was found, from `walk-1/` alone:

With the MobileDrawBar swap wired in but 13H-3's
`annotateEffectiveHeight`/`drawClearance` measurement effect STILL ACTIVE, the
V390 canvas grew to **995px tall** (`V390_canvas_box: [61, 272.28, 268, 995]`)
and the walk's `draw_three_lines` step failed outright.

**Root cause of that regression:** the 13H-3 measurement effect scans
`[data-widget-embed-body] button[aria-label]` for the bottom edge of whatever
sits within `TOOLBAR_BAND_PX` (400px) of the body's own top, on the theory that
only a top-floating ChartToolbar could be there. MobileDrawBar's own tool/
control buttons (`Horizontal`, `Eraser`, `Undo`, `Redo`, `Snap to price`, `All
drawing tools`) all carry `aria-label` and, on the embed's normal ~300px base
height, sit well within that 400px band — so the effect measured MobileDrawBar
as if it were the very toolbar it exists to clear, and grew the body to roughly
`drawClearance + ANNOTATE_DRAW_BUFFER_PX(700)`.

**Why the complete fix needs no replacement clearance:** MobileDrawBar is
`position: absolute; bottom: 0`, a single fixed-height (~52-60px with padding),
never-wrapping row — the opposite shape of the old desktop `ChartToolbar`'s
~20-button roster wrapping to 3 rows (~170px, covering 57% of a 390px-wide/
300px-tall canvas). At the walk's own tap fractions (28/50/72% from the top),
the riskiest point for a BOTTOM-docked bar is the lowest tap (72% from top =
28% from bottom); on the measured ~300px base canvas that is ~84px of
clearance against MobileDrawBar's ~56-58px footprint — already clear without
any bump.

The workaround was therefore removed (widgetEmbedCore.js's
`annotateEffectiveHeight`/`ANNOTATE_DRAW_BUFFER_PX`, WidgetEmbedView.jsx's
`drawClearance` state + measurement effect + `TOOLBAR_BAND_PX`, and both its
test files). `EMBED_MAX_H` (the resize handles' own ceiling, unrelated to Draw
mode) was kept. walk-2/3/4 all confirm the canvas stays at its normal ~300px
height with the workaround gone.

## 8. The `/charts` control — the bare chart page is unchanged

`tools/notebook_w13h4_charts_control.py` (new, lane-owned, this lane's
8690-8694 port range) reuses 13H-3's own `run_bare_charts` helper
(`tools/notebook_w13h3_diag_walk.py`) against the SAME build this lane's own
walk ran against. `showDrawingTools`'s MobileDrawBar always passes real
`onUndo`/`onRedo` (StockChart.jsx ~line 19880), so §3's fix is a pure no-op
there by construction; this is the empirical proof.

**Final result (`charts-control-8/`): `VERDICT: PASS — 3 taps placed, 3
horizontal drawings stored`.** Per-tap detail: tool stays armed
(`ariaPressed: true`) across all three taps, stored count climbs 1→2→3,
sandbox integrity CLEAN.

**`run_bare_charts` itself needed two fixes first** — it carries 13H-3's own
docstring label *"DIAGNOSTIC-ONLY, not part of the lane's finish line"*, and
had in fact never been run to a real PASS against this exact page before
(`charts-control/` through `charts-control-7/` are the honest record of
finding out why, kept rather than deleted — same R-RAW idiom as walk-1
through walk-4 in §7). Neither fix touches anything this lane's own StockChart/
MobileDrawBar change is responsible for proving:

1. **The drawbar door is two steps, not one** (`charts-control/`:
   `TimeoutError` waiting for `"^Horizontal"`). The mobile /charts shell
   collapses drawing tools behind "More tools" (`MobileChartToolbar.jsx`) →
   a sheet whose "Draw on chart" row calls `expandDrawToolbar()`
   (`MobileMoreSheet.jsx`) — `run_bare_charts`'s fallback only ever looked for
   a bare `name=~"draw"` button already on the page, which does not exist
   until that sheet is open. Fixed by opening "More tools" first when the
   direct lookup finds nothing.
2. **Repeat mode defaults OFF, and a fresh sandbox browser has no stored
   preference** (`charts-control-2/` through `charts-control-7/`: 3 taps
   placed, only 1 line stored, unmoved by a 10s settle-wait — not a timing
   race). Diagnosed with per-tap `aria-pressed` reads
   (`charts-control-7/`): tap 1 placed a line and the tool deselected
   (`ariaPressed: true → false`, exactly what Repeat-OFF means), so taps 2–3
   landed on an unarmed canvas and did nothing. `charts-control-2/`
   through `-6/` also chased a canvas-resize red herring (the overlay
   canvas's cached box going stale) before the per-tap `aria-pressed` log in
   `-7/` isolated the real cause to repeat mode alone. Fixed by setting
   `localStorage['uct-draw-repeat']='true'` via `ctx.add_init_script` before
   the page loads — the same thing turning the real Repeat toggle on does.
   ⛔ **The first attempt at this fix silently did nothing**
   (`charts-control-6/`'s `bare_V390_repeat_flag` read back `None`):
   Playwright's `add_init_script` evaluates a passed string as a raw script,
   not a function to call, so `"() => { localStorage.setItem(...) }"` merely
   defined and discarded an unused arrow function. The working form is a
   plain top-level statement, no wrapping function.

Neither finding is a regression in anything this lane shipped — both are
pre-existing properties of the bare /charts page (its two-step mobile drawing
door, its default-off Repeat setting) that a diagnostic tool never built to
handle them simply hadn't been proven against before.
