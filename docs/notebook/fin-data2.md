## P4. The prep note was built before the trade closed

The walk says the AMD prep note was built after the trade closed. Its own record says
otherwise:

- `c2/walk.json` step 40, "one click builds the prep note": `2026-10-07T17:20:07`.
- step 41, "the prep note prints the member's own trade result": `17:20:07`, FAIL.
- step 52, "the AMD position closed at its target": `17:20:45`.

In `tools/notebook_fin_walk_features.py` the `earnings` step runs at line 826 and the `trades`
step, which closes the position, at line 975. The same record shows the Reporting soon box
listing AMD as "Open position" at 17:20:01, and the note naming "Your open positions" as a
source. So the note was built while AMD was open. It listed the open position and had no
closed trade to list. A prep note is frozen ("the values are frozen in this note"), so it does
not gain the trade later. This is a fault in the walk's step order, not in the product.

Every cause the brief named was checked against `earnings_prep._member_cells` (`:448`):

- Account filter: none. It calls `list_trades_for_user(user_id, spec=...)` with no account.
  A trade in a second account is listed (test).
- Date window: none. `FilterSpec(symbol=sym, limit=50)` carries no dates.
- Open versus closed: `j2_trades` holds closed trades only; a part close writes one (test).
- Paid gate: on the router, not on the trade read.
- Sample exclusion: not in this read. Samples are notes; this reads trades.
- Symbol: the filter is a prefix match, then narrowed to the name's own symbols (`wanted`).
- The walk's door: `POST /api/j2/positions` then `/close`, the member's own door. The reader
  sees it (test).

The server value is the journal's fraction: 341.28 to 514.93 gives `pnlPercent` 0.5088, which
rounds to 0.509 and prints as "+50.9%" through the note's formatter.

Tests, all through the journal's own routes (open a position, close it):
`test_a_trade_closed_through_the_journal_is_in_a_prep_note_built_after_it`,
`test_a_prep_note_built_before_the_close_has_no_trade_and_says_so`,
`test_a_part_close_lists_the_trade_and_the_shares_still_held`,
`test_a_trade_in_a_second_account_is_still_the_members_trade`. Two mutations, both red.

For the walk lane: move the percent check after the `trades` step, or close AMD before the
`earnings` step. Then "+50.9%" can be confirmed in a browser. It was not confirmed in one here.

## P7. The payload says what is unavailable, and why

**Review drafts.** With plan grading off, `discipline` is null and nothing said why. The draft
now also carries:

    "disciplineOmitted": null                       (plan grading on)
    "disciplineOmitted": {"reason": "plan_grading_off",
                          "sentence": "Plan grading is switched off, so this draft has no discipline record."}

`reason` is the stable key. The sentence is a default; lane FE2 owns the wording. Nothing else
changed: with plan grading off a draft still grades nothing and writes nothing.

**Setups board.** The empty board tells the member to draw an entry line on a chart in a plan
note. That is the chart plan panel, which has its own switch. The board now carries:

    "planDrawing": {"available": true,  "reason": null,             "sentence": null}
    "planDrawing": {"available": false, "reason": "chart_plan_off", "sentence": "Drawing a plan on a chart is switched off, so no new setup can be added here yet."}

It is read from `chart_plan.enabled()`, the chart plan's own gate, and not restated.

## P8. Removing the sample removes the folders the sample made

`sample_notebook.remove` now deletes the folders the seed made.

**How a folder is identified.** Never by name. A folder row has no marker column, and the
`notebook_sample` preference can be written by a client (round 1, M3), so neither can decide.
The durable fact is the notes' own marker (`import_source = 'sample'`). A folder is the
sample's when it was made while the marked notes were being written: between the first marked
note, less two seconds, and the last. So:

- a folder the member made earlier, which the seed only reused, is kept;
- a folder the member made later, whatever its name, is kept;
- a folder a sample note was moved into is kept;
- a sample folder the member emptied by moving its notes out is still removed.

**When a sample folder is kept.** When it holds a note that is not a sample note (live,
archived or in Trash), it is kept and nothing in it is moved. A folder that holds a kept folder
is kept too. The answer says so:

    "foldersRemoved": [{"id", "name"}]
    "foldersKept":    [{"id", "name", "memberNotes", "sentence"}]

for example `The folder "Capability examples" has 1 note of yours in it, so it was kept.`

The sample's notes stay in Trash and can still be restored. The Notebook's own folder delete
moves them up one level, so a restored sample note comes back outside the deleted folder.

Six tests, four mutations, all red.

**Limits, stated plainly.** The two seconds exist because the seed writes its folder just
before its first note. A member who makes an empty folder and adds the sample within two
seconds, and never puts a note of their own in it, would lose that empty folder on removal.
A marker column on the folder table would remove even that; it is a schema change and was
left for a ruling.

## P9. An example chart is never matched, and the answer says so

Confirmed by code: `similar_matches.templates_for` drops sample charts with
`sample_marker.without_sample_notes` (round 1, I3). `templates: 0` in the walk is that rule
working. A new test runs the nightly job over a tagged sample chart: no template, no row.

The matches answer (`GET /api/j2/similar-names/{note}/{embed}`) for a sample note is now:

    "status": "example", "matches": [], "asOf": null,
    "template": {..., "example": true},
    "neverMatched": {"reason": "sample_example",
                     "sentence": "This chart is an example, so it is never matched. Tag a chart of your own to find names like it."}

For a member's own chart only two keys are added: `neverMatched` null and `template.example`
false. Rows stored for a chart before it was known as an example are not shown.

Each setups-board card carries `similarNeverMatched`, true for an example.

For lane FE2: the client shows the "matched tonight" line only for `status === 'pending'`, so
an example now shows no line until FE2 words the new status.
