# The two F5 changes ruled by D3 — design note (wave 5, 2026-09-23)

**Ruling.** `NOTEBOOK-10-OF-10-PLAN.md` §3, **D3**: the F5 freeze is lifted for exactly
two changes — **F5P-1** (queued words never leave while the member sits on the note) and
**the append-merge finding** (a server-appended widget, fact or excerpt dropped by an
offline sync). Nothing else under the freeze moves. The amendment is recorded in the
freeze rail itself (`app/src/pages/journal-2-0/lib/offline/f5Freeze.test.js`, header,
"AMENDED 2026-09-23 — DECISION D3"), per that rail's own procedure.

**Invariants every change here keeps** (Wave Q1, `wave-q1-RESUME-HERE.md`): one writer per
note · conflict-fork-never-clobber · the durable record and its outbox intent move in one
transaction · `discardsUnsentWork` (a record with unsent words is never reconciled away) ·
the kill switch (`NOTEBOOK_OFFLINE_DEFAULT_ON` / `OFFLINE_DEFAULT_ON`: off writes nothing).

### A.3 The mechanism, and the two fixes

**A-1 — the base.** `settleLandedSave` (`lib/offline/useDurableNote.js`), when the record
still holds unsent work (Q1 fix 4), keeps `prev`'s words **and** `prev`'s baseline — but it
wrote `serverBase: snapshotOfServerCopy(acked, landed)`. After an append door, `acked`
already contains the node. The drain later diffs the server against that base, reads
*metadata-only*, rebases the queued body (which never had the node) and sends it. The node
is gone — and by the same arithmetic a body another device rewrote between the two
revisions would have been overwritten, which is a clobber. **Fix:** in the unsent-work
branch the base is the copy those words were written on — `lastKnownServerCopy(prev)` —
falling back to `acked@landed` only when `prev` has none (the old behaviour).

**A-2 — the predicate.** `discardsUnsentWork` (`lib/offline/recoverLocalState.js`)
answered "unsent work" for any `incoming ≠ prev`. When the editor has merged the server's
block and saved, what landed is `prev`'s words **plus** that block — nothing of `prev` is
missing — yet the settle kept the record dirty with a queued entry that lacks the block,
and the drain later forked the member's own note. **Fix:** not a discard when it is
*proven* that `incoming` holds `prev` exactly plus only server-appended blocks at the tail:
identical title and subtitle, every one of `prev`'s blocks in place and byte-identical, the
extras all `widgetEmbed` / `financialFact` / `documentExcerpt` (`appendedServerNodes`, the
drain's own proof). A member-typed tail, a changed paragraph, an append in the middle, a
title or subtitle edit, or a block removed all still read as a discard.

⚠️ **Residual, stated rather than hidden.** `acked` is a claim. A future caller that passed
LOCAL state as `acked` (the fix-4 lie) whose local state happened to be the record plus a
member-inserted widget / fact / excerpt at the very end would now read as caught up. No
caller does: `commitSave` and `restoreDraft` pass what the server accepted,
`settleMetadataRevision` what it returned. `selfForkDoors.test.jsx`'s lie rail still holds
for every other shape.

## §B — F5P-1: words queued for the open note (D3 change 1)

### B.1 The state, measured on the real editor before any change

F5P-1 (`q1-product-followups.md`) was observed on production: after returning to a note
with queued offline words, nothing was sent for 120 s. The mechanism, confirmed on the
committed editor with a rail that mounts it next to the real sweep:

- the sweep skips the note the editor owns — `excludeNoteId` (`NotebookTab.jsx` passes the
  route's note); that is Q1's single-writer rule, and it stays;
- the editor reopens on the **server's** copy and puts the queued words behind the
  *"Unsaved changes from a previous session"* Restore / Discard banner; its save gate then
  finds nothing changed, so it sends nothing.

The rail (§B.4) against the committed editor: **4 / 4 send cells RED** — the words never
leave — with nobody typing, for every server state (unchanged, a metadata door, an append
door, a second writer).

### B.2 The design

**The owner sends them.** Queued words are not a crash draft: the member already committed
them to the server, the sweep sends them without asking the moment the note closes, and
compare-and-set on their own baseline makes sending them unable to clobber anything. So the
editor — the single writer that owns the note — *adopts* them and sends them through its own
save:

1. `recover()` (the call the editor already makes on open) now returns `adopt` for
   **provably queued** work: a dirty durable record with its outbox entry, not blocked, an
   unambiguous winner that is exactly the queued words, and a known server copy those words
   were written on. Everything else — a crash draft, two unorderable copies, a blocked entry
   — still gets the banner, unchanged.
2. The editor holds `adopt.state` and sets its baseline to **`adopt.base` — the copy the words
   were written on, never the server's current revision** — then saves normally. If the
   server moved, the PUT 409s and the editor's existing `reconcileConflict` decides with the
   same classifier the drain uses: metadata ⇒ rebase, append ⇒ merge the block, anything else
   ⇒ fork, never clobber.
3. When that fork happens, the editor settles the durable copy with the drain's own fork
   settle (`settleOwnerFork` → `settleForkedNote`), so the sweep does not fork it a second
   time once the note closes.

**Rejected, and why.** *Let the sweep send the open note:* a second writer — the editor would
keep the stale copy and fork on the member's next keystroke. *Adopt on the server's current
revision:* measured below — it drops a door's appended widget and overwrites a second writer.

### B.3 Found on the way, and folded in: Restore clobbers a moved server

Measured on the committed editor (scratch probe, deleted after): with the server moved by a
second writer, **Restore** PUTs on the recovered copy's baseline, gets a 409, sets an error —
and leaves the editor on the **server's current revision**. The member's next keystroke
autosaves the recovered words over the other device's: `other device words survive: false`,
`forks: 0`. After an append door the captured block goes the same way. It is live today
wherever the banner appears after the server moved. The editor could not do better because
nothing told it what the recovered words were written on, so `recover()` now also returns
`base` (`baseOfRecovered`, the same authority `adopt` uses), and Restore adopts on it (E-2).

### B.4 What landed in the offline layer (this commit), and what the editor must add

| where | what |
|---|---|
| `recoverLocalState.js` | `queuedWorkToAdopt` (the decision) and `baseOfRecovered` (the one authority on "written on which copy") |
| `useDurableNote.js` | `recover()` returns `adopt` and `base`; `settleOwnerFork` (store-direct, mount-independent, inert with the kill switch off) |
| `outboxDrain.js` | `settleForkedNote` exported — the drain's own fork settle by note id; the sweep's `settleForked` is now a one-line call to it (no behaviour change) |

⛔ **BLOCKED ON THE EDITOR (owner: EDITOR agent — `NoteEditorPage.jsx` is theirs).** The
change is written, and proved against a relocated copy of the committed editor (never the
real file):

- **E-1** — the recovery effect sets `pendingAdoption` when `decision.adopt` is present
  (no banner); an effect declared after the hydration gate applies it: the words into the
  editor, `lastSavedRef` = `adopt.base`, then the ordinary autosave.
- **E-2** — `restoreDraft`: when `recovery.base` is known, restore through the same adoption
  instead of the direct PUT (unchanged for a crash draft with no recorded base).
- **E-3** — `reconcileConflict`'s fork branch: `await settleOwnerFork(...)`, then
  `markSynced` with the server copy, before `clearDraftLocally()`.
