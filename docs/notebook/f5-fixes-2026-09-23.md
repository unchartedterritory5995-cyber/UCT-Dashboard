# The two F5 changes ruled by D3 — design note (wave 5, 2026-09-23)

**Ruling.** `NOTEBOOK-10-OF-10-PLAN.md` §3, **D3**: the F5 freeze is lifted for exactly
two changes — **F5P-1** (queued words never leave while the member sits on the note) and
**the append-merge finding** (a server-appended widget, fact or excerpt dropped by an
offline sync). Nothing else under the freeze moves. The amendment is recorded in the
freeze rail itself (`app/src/pages/journal-2-0/lib/offline/f5Freeze.test.js`, header,
"AMENDED 2026-09-23 — DECISION D3"), per that rail's own procedure.

**Invariants every change here keeps** (Wave Q1, `wave-q1-RESUME-HERE.md`): one writer per
note · conflict-fork-never-clobber · the durable record and its outbox intent move in one
transaction · `discardsUnsentWork` (a record with unsent words is never reconciled away) ·
the kill switch (`NOTEBOOK_OFFLINE_DEFAULT_ON` / `OFFLINE_DEFAULT_ON`: off writes nothing).

### A.3 The mechanism, and the two fixes

**A-1 — the base.** `settleLandedSave` (`lib/offline/useDurableNote.js`), when the record
still holds unsent work (Q1 fix 4), keeps `prev`'s words **and** `prev`'s baseline — but it
wrote `serverBase: snapshotOfServerCopy(acked, landed)`. After an append door, `acked`
already contains the node. The drain later diffs the server against that base, reads
*metadata-only*, rebases the queued body (which never had the node) and sends it. The node
is gone — and by the same arithmetic a body another device rewrote between the two
revisions would have been overwritten, which is a clobber. **Fix:** in the unsent-work
branch the base is the copy those words were written on — `lastKnownServerCopy(prev)` —
falling back to `acked@landed` only when `prev` has none (the old behaviour).

⚠️ **This is a deliberate exception to what a frozen file says (review N1).**
`serverChange.js:185-187` describes `serverBase` as *"moved forward every time the server
tells us something newer (an ack, a successful drain send)"*. After A-1, an ack that lands
while the record still holds unsent work does **not** move it — that is the whole fix. The
frozen file cannot be edited under D3, so the exception is recorded here and at the settle
itself (`useDurableNote.js`, the comment above `const state = unsentWork ? prev : …`).

**A-2 — the predicate.** `discardsUnsentWork` (`lib/offline/recoverLocalState.js`)
answered "unsent work" for any `incoming ≠ prev`. When the editor has merged the server's
block and saved, what landed is `prev`'s words **plus** that block — nothing of `prev` is
missing — yet the settle kept the record dirty with a queued entry that lacks the block,
and the drain later forked the member's own note. **Fix:** not a discard when it is
*proven* that `incoming` holds `prev` exactly plus only server-appended blocks at the tail:
identical title and subtitle, every one of `prev`'s blocks in place and byte-identical, the
extras all `widgetEmbed` / `financialFact` / `documentExcerpt` (`appendedServerNodes`, the
drain's own proof). A member-typed tail, a changed paragraph, an append in the middle, a
title or subtitle edit, or a block removed all still read as a discard.
⭐ **Since fix round 1 (review N2) that proof is not restated — it is ASKED.** After the
`sameAuthoredContent` early return, the predicate is exactly
`classifyServerChange(incoming, prev) !== APPEND_ONLY`: the drain's own classifier, called
from `recoverLocalState.js`, never edited. The restated copy (`holdsWithServerAppends`) is
gone; it already differed from the classifier in how it read a missing title (`?? ''`
against `str()`), and a field added to the classifier later would have been missed here.

⚠️ **Residual, stated rather than hidden.** `acked` is a claim. A future caller that passed
LOCAL state as `acked` (the fix-4 lie) whose local state happened to be the record plus a
member-inserted widget / fact / excerpt at the very end would now read as caught up. No
caller does: `commitSave` and `restoreDraft` pass what the server accepted,
`settleMetadataRevision` what it returned. `selfForkDoors.test.jsx`'s lie rail still holds
for every other shape. ⭐ Since fix round 1 (review N3) that sentence is a rail, not a
reading: `settleLandedSaveCallers.test.js` walks `app/src` by AST and pins every caller of

this residual.

## §B — F5P-1: words queued for the open note (D3 change 1)

### B.1 The state, measured on the real editor before any change

F5P-1 (`q1-product-followups.md`) was observed on production: after returning to a note
with queued offline words, nothing was sent for 120 s. The mechanism, confirmed on the
committed editor with a rail that mounts it next to the real sweep:

- the sweep skips the note the editor owns — `excludeNoteId` (`NotebookTab.jsx` passes the
  route's note); that is Q1's single-writer rule, and it stays;
- the editor reopens on the **server's** copy and puts the queued words behind the
  *"Unsaved changes from a previous session"* Restore / Discard banner; its save gate then
  finds nothing changed, so it sends nothing.

The rail (§B.4) against the committed editor: **4 / 4 send cells RED** — the words never
leave — with nobody typing, for every server state (unchanged, a metadata door, an append
door, a second writer).

### B.2 The design

**The owner sends them.** Queued words are not a crash draft: the member already committed
them to the server, the sweep sends them without asking the moment the note closes, and
compare-and-set on their own baseline makes sending them unable to clobber anything. So the
editor — the single writer that owns the note — *adopts* them and sends them through its own
save:

1. `recover()` (the call the editor already makes on open) now returns `adopt` for
   **provably queued** work: a dirty durable record with its outbox entry, not blocked, an
   unambiguous winner that is exactly the queued words, and a known server copy those words
   were written on. Everything else — a crash draft, two unorderable copies, a blocked entry
   — still gets the banner, unchanged.
2. The editor holds `adopt.state` and sets its baseline to **`adopt.base` — the copy the words
   were written on, never the server's current revision** — then saves normally. If the
   server moved, the PUT 409s and the editor's existing `reconcileConflict` decides with the
   same classifier the drain uses: metadata ⇒ rebase, append ⇒ merge the block, anything else
   ⇒ fork, never clobber.
3. When that fork happens, the editor settles the durable copy with the drain's own fork
   settle (`settleOwnerFork` → `settleForkedNote`), so the sweep does not fork it a second
   time once the note closes.

**Rejected, and why.** *Let the sweep send the open note:* a second writer — the editor would
keep the stale copy and fork on the member's next keystroke. *Adopt on the server's current
revision:* measured below — it drops a door's appended widget and overwrites a second writer.

### B.3 Found on the way, and folded in: Restore clobbers a moved server

Measured on the committed editor (scratch probe, deleted after): with the server moved by a
second writer, **Restore** PUTs on the recovered copy's baseline, gets a 409, sets an error —
and leaves the editor on the **server's current revision**. The member's next keystroke
autosaves the recovered words over the other device's: `other device words survive: false`,
`forks: 0`. After an append door the captured block goes the same way. It is live today
wherever the banner appears after the server moved. The editor could not do better because
nothing told it what the recovered words were written on, so `recover()` now also returns
`base` (`baseOfRecovered`, the same authority `adopt` uses), and Restore adopts on it (E-2).

### B.4 What landed in the offline layer (this commit), and what the editor must add

| where | what |
|---|---|
| `recoverLocalState.js` | `queuedWorkToAdopt` (the decision) and `baseOfRecovered` (the one authority on "written on which copy") |
| `useDurableNote.js` | `recover()` returns `adopt` and `base`; `settleOwnerFork` (store-direct, mount-independent, inert with the kill switch off) |
| `outboxDrain.js` | `settleForkedNote` exported — the drain's own fork settle by note id; the sweep's `settleForked` is now a one-line call to it (no behaviour change) |

✅ **The editor half LANDED as `fe4e278bc`** — applied by the EDITOR agent (whose file
`NoteEditorPage.jsx` then was) from this handover, with the end-to-end rail in the same

## §C — Review fix round 1 (`wave5-A-review.md`)

The review found two ways the landed change could lose words the member typed **while it was
working** (S1, S2) and nine notes. By then the EDITOR agent had finished, so the editor
changes below were made in `NoteEditorPage.jsx` directly and land with their rails.

### C.1 S1 — the owner's fork settled away words typed during the create request

**The loss (review S1).** E-3 captured the local copy, `await`ed `createNoteViaApi` (a network
round trip), showed the server copy, then settled the store clean and `markSynced` the server
copy. Words typed during the create reached the record, the queue and the draft but not the
sibling, and all three were then cleared — the words were in no layer.

**The fix — the sibling must still be the whole truth, asked in three places.**

| where | check | when it matters |
|---|---|---|
| `settleOwnerFork({…, forked})` | the record and every queued entry for the note still equal `forked` (title, subtitle, body); otherwise `false` and nothing is written. No `forked` ⇒ refused | the keystroke's durable write landed before the settle's read |
| editor, before calling it | the editor's own title, subtitle and body still equal `forked` (read before the view is replaced) | the keystroke is still inside the durable writer's 200 ms window |
| editor, after the settle's `await` | `markSynced` + `clearDraftLocally` only if the editor still equals the server copy | a keystroke on top of the server copy during the settle itself |

When a check fails the editor keeps the pre-E-3 behaviour: no settle, the queue keeps the words,
and a later second fork preserves them. A duplicate beats a loss. ⚠️ The store check and the
settle are two transactions — what can land between them is stated in `settleOwnerFork`'s own
comment.

### C.2 S2 — adoption put queued words over what the member was doing

**The loss (review S2).** (A) Typing before `recover()` resolved: adoption replaced the view,
reset the timer and overwrote the draft, while the fix-6 guard (correctly) kept the typing out
of the durable record — it was in no layer. (B) A save on the wire when adoption ran: its 200
moved `lastSavedRef` to its own revision, and the adoption's save then went out on that
revision with no 409, over the member's words and any door's block.

**The fix.** Queued words are adopted silently only while the member has not edited this note
since it hydrated; otherwise they are **offered** (the banner, built from the same decision —
the `HEAD~1` behaviour, which keeps both copies). A **Restore** is the member's own choice, so
an edit does not stop it, but a save already on the wire is waited for (the adoption re-runs
when that save settles, success or failure) and never raced.

⚰️ **The review's rule names two halves — "not edited" and "no save pending or in flight" —
and one of them was deleted after it was measured.** The first version checked both (`edited ||
saveTimer || retryTimer || inFlight`). Removing the second term left every rail green. The hazard
it stood for is a save that, when it lands, moves `lastSavedRef` under the adoption, so the
adoption's send goes out on the new revision with no 409. ⚰️ **The premise first written here
was too broad** (re-review point 1): it said *"after hydration a save is only ever pending or on
the wire downstream of `scheduleAutosave`"*, and the metadata doors, the excerpt door, a version
restore and the crash-draft Restore all reach the wire without it. The conclusion survives on the
narrower premise, checked against every writer of `lastSavedRef`: the metadata and excerpt doors
never touch it (an adoption during one still sends on its base and 409s into the reconcile); the
crash-draft Restore comes only from a banner decision, exclusive with an automatic adoption; a
version restore does move it but loses no words in either order; and `commitSave`, its retries
and its unmount flush really are downstream of `scheduleAutosave`, which marks the note edited
before it arms anything. A term that cannot be true without the other one is a guard that reads
as protection and cannot fire; the derivation is written at the check instead. The in-flight
flag itself is load-bearing — for the Restore wait — and has its own cell.

## §D — Review fix round 2 (re-review in `wave5-A-review.md`)

### D.1 N4, the Restore half — one authority for "a base the entry disagrees with"

Round 1 refused the automatic adoption of a record written before A-1 (its base `acked@landed`
already holds a door's block, its entry sits on the older revision). Restore still read the same
poisoned base through `baseOfRecovered` and sent the queued body at `landed`: a 200, and the
block gone. **The check now lives in `baseOfRecovered`, given the entry**, and
`queuedWorkToAdopt` asks it rather than repeating it. `recover()` passes the entry, so both doors
see the same answer: the banner offers the words, and Restore takes its path for a copy with no
known base (a direct PUT on the words' own revision), which is the behaviour before E-2.
⚠️ Stated rather than hidden: after that direct PUT's 409, a keystroke can still overwrite — the
crash-draft class §C.5 leaves open by ruling. What is closed is Restore sending the words on a base
the entry disagrees with. Without an entry there is nothing to compare, and the record's own base
is returned as before.
⚰️ **Narrowed in fix round 3 (§E):** "disagrees" now means NEWER than the entry. A base OLDER than
the entry is a legitimate shape and is used again, as it was at `fe4e278bc`.

### D.2 R2 — the editor's own S1 gate, isolated

A keystroke still inside the durable writer's 200 ms window when the sibling lands is invisible to
`settleOwnerFork`'s store gate — the record still equals what was forked. Only the editor's check
of its own view stops the settle. The new cell types during the create request and releases it
with no clock movement.

### D.3 Comments (R3)

- `settleOwnerFork`: "three IndexedDB transactions", and the protection named correctly — the
  editor's post-settle re-read, not the writer's debounce.
- The S2 premise, in §C.2 above and at the check in the editor: "a save that moves
  `lastSavedRef`", not "a save".

### D.4 R1 — flush before the view swap

⚰️ **§C.1's "the queue keeps the words, and a later second fork preserves them" held only once
the words were in the store** (this also corrects the review's original S1 claim about
`HEAD~1`). When the member keeps typing across the fork, the editor gate correctly refuses the
settle, but the words typed during the create are still the durable writer's PENDING snapshot,
and the writer keeps only its newest one: the next keystroke on the server copy superseded them
before they were written (the fix-6 guard then kept the record's older words against `fresh+K2`),
and the draft that held them was overwritten by the same keystroke. **Fix, one line:** when the
view has moved (`!editorHoldsForked`), `durableRef.current.flush()` BEFORE `setContent(fresh)`.
`flush` takes the pending snapshot synchronously, so the words are written as `record + K`, the
fix-6 guard keeps them against later keystrokes, and the queue carries them to a second fork.
⚠️ Residual, stated: a `flush` while a durable write is already in flight defers to it, so a

### E.1 Only a base NEWER than the entry is refused

§D.1's check refused any base whose revision differed from the queued entry's. The re-review
found that this also caught **legitimate** mismatches that `fe4e278bc` handled safely on both
doors, and regressed them to the banner plus a Restore that can be overwritten by a later
keystroke. The commonest: the editor's 409 reconcile moves `lastSavedRef` forward, the retry does
not land, and the next durable write takes the newer baseline while the record keeps its older
last-known copy. The drain's ring-vouched rebase does the same (it moves the entry and never sees
the server's document).

**The rule now** (`baseOfRecovered`, still the one authority):
- **Base OLDER than the entry → used, exactly as at `fe4e278bc`.** Diffing the server against an
  older copy can only see more change, so the 409 rebases, merges or forks. It can never hide an
  append.
- **Base NEWER than the entry → refused.** This is the poisoned shape (`acked@landed`), and §D.1's
  fallback stands for it.
- **Equal → used.** Unparseable, or an entry with no baseline → refused.
- Compared **parsed**, through `isSupersededBaseline`, the comparator the drain already uses. It
  is never compared as strings.

⚠️ **Stated rather than hidden:** a base newer than the entry is not always poison. A drain
rebase that learned the server's copy moves the entry and the base together. A later unsent-work
settle then re-derives the entry's baseline from the record's older one. That shape cannot be
told from the poisoned one by direction, so it is refused too. Its Restore takes the
no-known-base path, which a later keystroke can overwrite. That is the crash-draft class (§C.5).
The fork-safe fallback that would close it is scheduled for wave 6 lane D3b, not done here, by
ruling. ⚰️ §D.1's docstring example of a legitimate mismatch, "a rebased entry", was wrong:
`rebaseEntry` moves the entry and the base together.

### F.1 The per-note owner lock (item 1)

**The defect.** `excludeNoteId` is per mount, and only the leading tab sweeps. With a note open in
tab A and tab B leading, B's sweep sent A's queued words while A's editor — which adopts and sends
those same words itself (F5P-1, §B) — was still their writer. A's own send then 409'd against its
own words, classified BODY_REWRITE against the base the words were written on, and **forked the
member's note with nobody else writing** (property family D3b · 1 below: 12 of 42 orderings, RED
on the pre-D3b code).

**The fix.**
- `lib/offline/noteOwnerLock.js` (new): `holdNoteOwnerLock(accountId, noteId)` holds the Web Lock
  `uct-note-owner:<accountId>:<noteId>`, mode `exclusive`, until released; released on `pagehide`
  and taken again on a `pageshow` that restores the page from the back-forward cache.
  `ownedNoteIds(accountId)` reads `navigator.locks.query()` and returns the ids whose lock is HELD
  **or QUEUED** in any tab (a second tab opening the same note queues behind the first, and is still
  an editor), or **`null` when the browser cannot say**. `isNoteOwned` is the per-note shape.
- `useDurableNote` (the hook the editor already mounts, and nothing else mounts) holds the lock for
  the life of the mount. No edit to `NoteEditorPage` for this item.
- `drainOutbox` (frozen; D3b) takes `noteIsOwned` and SKIPS an owned note — asked at the top of the
  loop (so an owned note is never touched: no server question, no pre-send rebase of its entry) and
  **again right before the send** (the checks between can include a network round trip). A null, a
  throw, or no predicate is UNKNOWN, and unknown is never "owned": `excludeNoteId` alone decides,
  exactly as before.
- `useOutboxDrain` passes `noteIsOwned: (id) => isNoteOwned(accountId, id)`, asked fresh per entry.

**Where Web Locks are missing** (an old engine, an insecure context): no lock is taken, nothing
throws, `ownedNoteIds` answers `null`, and the sweep is byte-identical to before (rail: the same
fixture drained with the option and without it returns equal results). Without Web Locks no tab
leads (`READ_ONLY_FOR_SYNC`), so no tab sweeps at all. **No timeout** on the lock: the browser
releases it when the document dies.

⚠️ **Residual, stated.** A sweep that passed its last check before the note opened can still have
its PUT in flight while the editor adopts the same words; if the editor's send then lands second it
409s against identical content and forks. The window is one PUT round trip against the open + the
~800 ms autosave; closing it needs the editor's reconcile to notice "the server already holds
exactly my words" — an editor change outside this lane.
✅ **Closed in fix round 1 (§G.1):** the reconcile now asks `ownerReconcilePlan`, which answers
LANDED for exactly that, and the editor settles it as a 200.

### F.3 The owner's fork settle is ONE transaction (item 3)

**The defect (re-review 1 point 2; S1 residual).** `settleOwnerFork` read the record, read the
queue, then called `settleForkedNote` — three transactions. A durable write landing after the last
read (another tab's editor on the same note, an unmount flush) was overwritten with the server copy
and its queued entry deleted.

**The fix.**
- `notebookDb.putNoteWithIntentIf(db, noteId, decide)` (new): ONE readwrite transaction that reads
  the record and the note's queued entries (its `byNote` index), asks `decide(record, queued)`
  synchronously, and writes — or not — before the transaction ends. The writes are
  `putNoteWithIntent`'s own, staged by one function (`stageNoteWithIntent`), so its null-intent
  guard still lives in exactly one place.
- `settleForkedNote(db, noteId, serverNote, { forked })` (frozen; D3b): with `forked`, the check
  (record and every entry equal `forked`) and the write are that one transaction; without it (the
  sweep) the old path, byte for byte. The record both write is one function (`forkSettledRecord`).
- `settleOwnerFork` is now `settleForkedNote(…, { forked })`.

**Why the fake store needed a mode.** The in-memory IndexedDB snapshots each transaction at
creation and commits by replacing whole stores, so two readwrite transactions alive at once lose
each other's writes — harmless for rails that never overlap two writers, exactly wrong for this one.
`createFakeDb({ serialize: true })` (opt-in; every existing rail keeps the default) starts a
readwrite transaction only after every earlier one has committed and takes its snapshot at START,
as IndexedDB orders them. Two controls prove the difference both ways.

### F.4 A flush persists the latest snapshot behind an in-flight write (item 4)

**The defect (re-review 2 (a); R1 residual, §D.4/§E.3).** The refused-fork fallback flushes the
words typed during the fork and then swaps the view. With a durable write already in flight the
flush returned early, the words stayed the writer's `desired` snapshot, and the member's next
keystroke on the new view — a `schedule` — replaced them before they were written. The fix-6 guard
then kept the older record against the new view: the words were in no layer.

**The fix (`durableWriter.js`).** A flush during an in-flight write PINS the current snapshot:
written right after the in-flight one, before anything scheduled later, which still follows as the
one coalesced newest state. Without a flush, coalescing is unchanged. A pinned snapshot whose write
fails is kept and retried first; a destroyed writer starts no new work but still writes what a flush
pinned (so the unmount flush behind an in-flight write is no longer dropped); `isDurable` counts
pinned snapshots.

### G.1 Residual (a) — a sweep PUT already in flight as the note opens

**The defect (§F.1's residual).** Tab B's sweep passes its last owner-lock check while the note is
still closed, and its PUT of the queued words goes on the wire. Tab A opens the note and its editor
adopts the SAME words on the revision they were written on. B's PUT lands them; A's own send then
409s, and the reconcile classified the server's copy against A's base, read the member's own words
as the server's change (BODY_REWRITE), and **forked the member's note with nobody else writing**.

**The fix.**
- `lib/offline/ownerReconcile.js` (new): `ownerReconcilePlan({ fresh, base, sent })` — ONE authority
  for what the owning editor does with a 409. When the server's copy is byte-identical in authored
  content to EXACTLY what the 409'd send carried (`sameAuthoredContent` — the drain's own
  "identical ⇒ ours" test in `serverCopyIsOursDefault`), the answer is **LANDED**: the words reached
  the server one revision later, and nothing conflicted. Otherwise `classifyServerChange` against
  the base decides, exactly as before (RETRY for metadata/append, FORK for anything else).
- `NoteEditorPage.jsx`: `reconcileConflict(sent)` asks the plan; `commitSave` settles a LANDED 409

  a second copy of it. The rest of the 409 handling is unchanged; it moved into an inner `catch` so
  both answers reach the same settle.
- The property rail's model of the owning editor now asks `ownerReconcilePlan` too, so the model
  cannot drift from the editor.

**Why nothing is lost.** LANDED requires the server to hold every word that was sent. Anything typed
since is ahead of that; it stays the editor's (and the durable store's) and goes out on the server's
revision — railed ("a keystroke typed after the landing still goes out"). A server that differs by
anything (another device's sentence, a door's block, a title) is not LANDED — railed by a control
that must still fork.

### G.2 Residual (b) — a cleared title on a revision-only Restore (N-6)

**The defect.** A revision-only base reads `''` for title and subtitle, and `commitSave` sent a
field only when it differed from the base, so a restored copy whose title or subtitle the member
had CLEARED sent no title at all. With the server unmoved the PUT was a 200 and the old title stayed:
**no words lost, the clearing EDIT lost** (§F.2 said "nothing is lost", corrected there).

**The fix (`commitSave`).** A base with no body proves nothing about the title either: when
`lastSavedRef.bodyJson` is null the title and subtitle are sent as they stand ("compare against
unknown ⇒ treat as changed"). ⭐ **Keyed on the missing BODY, not on `bodyUnknown`**, because the flag
cannot survive the durable store: `snapshotOfServerCopy` (frozen) keeps no `bodyUnknown`, so the next
session rebuilds the same base as a plain copy with a null body, `queuedWorkToAdopt` adopts it, and a
flag-keyed fix would drop the clear again there — railed separately. Harmless where the server's
body is genuinely null: under compare-and-set, sending the fields as they stand writes nothing but
what the member holds, on the revision the base names (and the body is always sent against a null
one anyway). A CONTROL pins that a known base still does not re-send an unchanged title.

### G.3 Residual (c) — the drain never classifies against a base that may not stand (RULING)

**The defect (§F.2's third residual; pre-existing, found by the review).** With the note closed, a
record settled before A-1 carries `acked@landed` as its base — a copy that already holds a door's
appended block — while its entry still sits on the older revision the words were written on. The
drain classified the server's copy against that base, read METADATA_ONLY, rebased the queued body
onto the server's revision and sent it: a 200, and the captured block was gone. Recovery has refused
that base since review N4; the drain had not.

**The ruling.** The controller extended the D3b lift: when the drain would classify against a
POISONED `serverBase` (newer than the queued entry's base) it treats the base as UNKNOWN and FORKS,
never rebases over it. Recorded as part of amendment D3b in `f5Freeze.test.js`.

**The fix (`outboxDrain.js`, frozen; the ruling).**
- `classifiableBase(entry, noteRec)` is now the ONE place the drain reads the last-known server
  copy. It asks `baseMayStandFor(base.updatedAt, entry.baseUpdatedAt)` — extracted from
  `baseOfRecovered` into `recoverLocalState.js` and asked by BOTH, so recovery and the sweep cannot
  disagree about which base is poison. Only a copy at exactly the entry's revision, or one PROVABLY
  older (parsed, `isSupersededBaseline`), may stand; a newer one — or one whose revision is missing
  or cannot be ordered — may not.
- `ringVouchedPlan(mine, noteRec, entry)` answers **'fork'** for a refused base (never the
  no-evidence rebase — a refused base is evidence the record moved past the words' revision). The
  pre-send path therefore rebases nothing and sends on the stale baseline, which 409s into the fork.
- The 409 diff branch classifies against `null` for a refused base, which the frozen classifier
  reads as BODY_REWRITE ⇒ fork.
- `classifyServerChange` itself (`serverChange.js`) is untouched; the ruling changed its INPUT.
  The freeze rail's new case pins that `lastKnownServerCopy(` is read exactly once in the drain,
  inside `classifiableBase`, that both deciders ask it, and that `baseMayStandFor` is defined once
  and asked by `baseOfRecovered`.

**The cost, stated.** §E.1's legitimate newer-than-entry shape cannot be told from poison by
direction, so the drain now forks it where it rebased: a spurious duplicate, never a loss — the same
trade recovery already made. An EQUAL or OLDER base still merges (two controls).

### G.4 N-1 — `oldestRevision`: the comment and the code agree, on the safe answer

The comment said a pair that cannot be ordered is "not guessed between"; the code returned the
parseable one of a mixed pair. **Kept the code, rewrote the comment**, because the parseable one is
the SAFE answer: the entry and the record are written together, so a mixed pair means one is
corrupt, and the parseable one is either the record's own revision (never newer than its entry in
any shape the product writes) or the entry's (the revision the sweep itself would send these words
on). Null would not be safer: it sends Restore back down the no-known-base path D3b closed — a direct
PUT that 409s into an error, the server's current revision, and a keystroke that overwrites another
device. Every shape is now railed (both parse ⇒ the older; mixed either way ⇒ the parseable one; a
lone unparseable ⇒ itself; two unparseable ⇒ null). The code did not change, so there is no RED on
the pre-fix product; mutation FN1 (the other reading, null for a mixed pair) proves the rails pin it.

### G.5 N-2 — a `query()` that never settles is unknown, and never stalls the drain

`ownedNoteIds` races `navigator.locks.query()` against `OWNER_QUERY_TIMEOUT_MS` (500 ms — a real
engine answers in milliseconds; this only bounds a query that never settles) and answers `null`
(unknown ⇒ exactly the pre-D3b behaviour) when the timer wins. The timer is cleared when the query
answers first; a late rejection after the bound is handled by the race. ⛔ A timeout on the QUESTION,
never on the lock. Rails: the bound (not a moment before, and not never), a drain with a lock manager
that never answers finishes and sends, the late answer, and a control (an answer in time is used and
leaves no timer).

### G.6 N-3 — a frozen tab lets go of its note

`holdNoteOwnerLock` drops the lock on the Page Lifecycle `freeze` and takes it again on `resume` —
both on the DOCUMENT (a new `doc` target, default `document`), not the window. A frozen tab runs no
script, so it cannot send its note; before this every other tab skipped the note for the whole
freeze. A tab frozen straight into the back-forward cache sees both pairs of events; each half is
idempotent, and a rail pins exactly ONE claim after `pagehide → freeze → resume → pageshow`. A tab
frozen while QUEUED behind another withdraws its request and queues again on resume.

### G.7 N-5 — a blocked entry reports BLOCKED, whoever has its note open

The `permanent` check moved to the top of the drain's loop, ahead of both "the editor owns it" skips
(`excludeNoteId` and the owner lock). It only reports — it sends nothing, asks nothing and writes
nothing — so it is safe ahead of both. Before, a blocked entry read SKIPPED whenever its note was
open, the same entry's status depended on which tab led, and `summarize().blocked` undercounted
exactly while the member was looking. A control pins that an owned entry that is NOT blocked is still
SKIPPED.
