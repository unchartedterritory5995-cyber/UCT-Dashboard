The resumed session's brief: runs 5-7 of the walk had instrumented a bug where Draw mode inside

## 2. The bug, measured

**Root cause.** `widgetEmbed` is `atom: true, selectable: true`. ProseMirror's own mousedown
handling (`prosemirror-view/dist/index.js`, `handlers.mousedown` → `MouseDown` → on the matching
mouseup, `selectClickedLeaf` → `updateSelection` → `view.focus()`) treats a mousedown anywhere
inside a selectable atom node as "the member may be about to click-select this node" and, on
release, calls `view.focus()` regardless of where inside the node the click landed — the chart's
own canvas, a drawing handle, anywhere that isn't a recognised `INPUT`/`BUTTON`/`SELECT`/
`TEXTAREA`. `WidgetEmbedView.jsx` listens for exactly that editor focus to mean "the member
clicked back into their prose, exit Draw mode" (`editor.on('focus', exit)`, there so the drawing
overlay's own keydown handling doesn't eat the editor's undo while writing). So every click or
drag on the chart's own drawing surface while annotating was read as a deliberate "done drawing"
and silently exited Draw mode after the first mark.

The exact call stack is in the run7 evidence's recorded `pm-focus` events:
`MouseDown.up → selectClickedLeaf → updateSelection → view.focus()`, all in
`prosemirror-view`. The mouseup listener that fires this chain is wired directly on `view.root`
by the mousedown handler, bypassing any node view's `stopEvent` entirely — so the only lever is
stopping the **mousedown**, not the mouseup.

**The fix** (this lane's commit `0d11a14787`): `widgetEmbedNode.jsx` now
registers a `stopEvent` on the node view (`ReactNodeViewRenderer(WidgetEmbedView, { stopEvent:
widgetEmbedStopEvent })`). `widgetEmbedStopEvent` is a pure, exported, unit-tested predicate:
a mousedown landing on `data-widget-embed-body` (the new marker on the chart's own rendered
surface — `WidgetEmbedView.jsx`'s body div) is told "not ProseMirror's business" unconditionally
(in Draw mode and out of it — the chart should always own its own clicks); every other case
mirrors TipTap's own default `stopEvent` (the `INPUT`/`BUTTON`/`SELECT`/`TEXTAREA`/
contentEditable passthrough, and the drag/drop/copy/paste/cut exceptions), because supplying
`stopEvent` at all REPLACES the default outright for this node type — the toolbar's own buttons
and the TF `<select>` had to keep behaving exactly as before.

Unit tests: `app/src/pages/journal-2-0/lib/widgetEmbedNode.test.js` (9 cases, the predicate in
isolation — no DOM/editor needed). Mutation M6
(`docs/notebook/evidence/wave13-13h2/mutation-M6-chart-body-click-reaches-prosemirror.log`):
removing the one `data-widget-embed-body` clause reds exactly the two tests that exercise it
(`stops a mousedown that lands on the chart body`, `stops a mousedown on an SVG drawing handle`)
and nothing else — 7 of 9 stay green, proving the clause is load-bearing and narrowly scoped.
Restored byte-identical, verified against the pre-mutation capture.

**Proof it is fixed, not just unit-tested:** before this fix, the walk never got past drawing the
first mark (runs 1-7, all FAIL at the "Horizontal Line" tool timing out because Draw mode had
already exited). After it, `V1200-2_draw_and_assign_roles` passes every run from run 9 onward —
3 lines placed, 3 stored, roles assigned, target > entry > stop.

## 5. Open item — the walk's own bug is fixed; a narrower, still-unexplained product gap remains

**Revision history of this section.** It previously named `ChartDrawingOverlay.jsx`'s touch
routing as the likely cause and recommended that file's owner investigate. **That theory is
retracted.** A controller follow-up ran an independent check against master's own `/charts`
page (390px and 820px touch, repeat ON and OFF) and placed 3/3 lines reliably, 12/12 stress
repeats — the shared `ChartDrawingOverlay` path does **not** lose touch taps on its own. This
section is rewritten from that correction and from run 19's new evidence, below.

### 5a. What the controller found, and what it fixed (real, and now closed)

The controller traced a genuine harness defect instead: both `MobileDrawBar.arm()` (the
touch drawing-tool rail) and `ChartToolbar.selectTool()` (the desktop toolbar) arm a tool with
`setActiveTool(activeTool === id ? null : id)` — a **toggle**. `draw_three_lines()`
(`tools/notebook_w13h2_walk.py`) pressed "Horizontal Line" before every one of the three taps,
unconditionally. If the tool was still armed from the previous placement, that extra press
would **de-arm** it immediately before the tap landed.

**The fix** (`tools/notebook_w13h2_walk.py::tool_armed_state`, this lane's commit `962bb4941b`):
before each tap, read whether the tool is currently armed — directly from the DOM, recorded in
raw evidence for every attempt, BEFORE the press decision is made — and press only when it is
not. Mobile's `MobileDrawBar` tiles set `aria-pressed`; desktop's `ChartToolbar` has no
`aria-pressed` at all, so the proxy there is an inset box-shadow, the **only** rule in
`ChartToolbar.module.css` that produces one (`.btn.active`). Both signals are recorded, never
guessed.

**Direct evidence the bug was real and is now fixed**, from run 19's raw `walk.json`
(`docs/notebook/evidence/wave13-13h2/walk-run19-armed-state-fix-toggle-confirmed-not-sole-cause/`):

| viewport | `armed_before_tap` across the 3 attempts | what the fix did |
|---|---|---|
| V1200 (desktop) | `false, false, false` | pressed every time (unchanged) — repeat reverts to unarmed after each desktop placement, so the old unconditional press was never wrong here |
| V390 (touch) | `false, true, true` | pressed on attempt 1 only; attempts 2 and 3 correctly skipped the press because the tool read as already armed — the exact toggle-trap the controller named |

V1200 stayed a clean 7/7 (`V1200_lines_after_tap`: stored count reaches 1, 2, 3, each within
the 10s settle window) — the fix changes nothing in the one case where the old code was already
correct, which is the needed non-regression proof.

### 5b. What the fix did NOT change: V390 still stores only 1 of 3 lines

With the toggle bug closed — confirmed by the table above, not a press being skipped by
accident — V390's `V390_lines_after_tap` reads:

```
attempt 1: stored_count=0, reached_in_10s=false
attempt 2: stored_count=0, reached_in_10s=false
attempt 3: stored_count=1, reached_in_10s=false
```

Each attempt's settle-loop polled the server every 0.3s for a full 10 seconds and never saw the
count increase for attempts 1 or 2 — not a persistence-lag reading (which would show the count
catching up on a LATER poll), a genuine non-registration. `V390_drawn` confirms the final state
holds exactly one line, at the same price as attempt 3's tap (consistent with every pre-fix run
back to run 9). **The toggle fix was necessary, proven correct, and not sufficient.**

### 5c. What this does and does not mean

- It does **not** reopen the `ChartDrawingOverlay.jsx` theory. The controller's own standalone
  test already settled that the shared component places taps reliably outside this embed; run
  19's result is consistent with that, not in tension with it — whatever is losing taps 1 and 2
  here is specific to this **touch + chart-embedded-inside-a-Notebook-note** combination, not a
  defect in the shared drawing overlay generally.
- It does mean the original V390 symptom (`docs/notebook/evidence/wave13-13h2/walk-run16-v390-settle-proof/`
  through `walk-run18-tool-match-ruled-out/`) was never explained by the toggle bug alone, even
  though the toggle bug was real, independently worth fixing, and is now fixed in this walk.
- The actual cause of "only the last of N rapid touch taps on an armed tool registers, inside
  this embed" is **not identified** by this lane's evidence. It is not attempted here: this
  lane's scope is the Notebook's own `ChartPanePanel`/`WidgetEmbedView` surface, and tracing a
  touch-event question down into the embedded chart's own touch pipeline — distinct from the
  already-cleared `ChartDrawingOverlay.jsx` shared-component path — is outside that scope and
  this lane does not have standing evidence pointing at a specific file to recommend.
