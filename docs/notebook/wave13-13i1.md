## 1. The fingerprint

A fingerprint is a JSON object:

```json
{
  "v": 1,
  "symbol": "NVDA",
  "requested_as_of": "2026-10-02",
  "as_of": "2026-09-30",
  "mode": "nightly",
  "fields": {
    "adr_pct": {"value": 5.9, "source": "screener_row", "missing": null},
    "rs_rank": {"value": null, "source": "screener_row", "missing": "rank_is_nightly_only"},
    "patterns": {"value": [{"setup": "vcp", "asof_date": "2026-09-29", "confidence": 81.2, "key_level": 100.1}],
                 "source": "pattern_vision", "missing": null}
  }
}
```

* `as_of` is the session the numbers describe (`null` when there are no bars at all).
  `requested_as_of` is the day asked for.
* `mode` is `nightly` (the requested day is covered by the nightly `screener_rows` row, so the
  row's columns are read) or `bars` (every field computed on stored daily bars up to and
  including the day, and nothing after it).
* Every field is `{value, source, missing}`. A field with a `missing` code has `value: null`,
  and a field without one has a value. Missing data is labelled, never invented.
* `tech_fingerprint.summary_values(fp)` flattens it to `{field: value}`. 13I-2's filters and
  13J's distance must read through it, so both pick the same values.

## 2. The chart-block index and the freeze

* `j2_chart_blocks` (auth.db, self-ensured): one row per chart block in a member's notes
  (`widgetEmbed` with `widgetId: chart`), key `(user_id, note_id, embed_key)`. `embed_key` is
  the node's `embedId`, else the legacy `chart|<capturedAt>`, with `#<position>` added on a
  clash. The block's day is the ET date of `params.to` (the frozen right edge), else of
  `capturedAt`. `setup_tag` and `note_fingerprint` are read from `attrs.ta.setupTag` and
  `attrs.ta.fingerprint`, the attr 13H-1 adds, when present.
* `j2_chart_fingerprints` (the freeze ledger): `(user_id, note_id, embed_key, symbol, as_of)`
  maps to the fingerprint computed once. Its only write is INSERT OR IGNORE.
* **Not in the save path, never a second writer.** `chart_blocks.catch_up(user_id, note_id=None)`
  reads the save path's own `j2_note_embeds` sidecar (`widget_id = 'chart'`) and each note's
  `updated_at`. It re-projects exactly the notes that changed (the per-note watermark is
  `j2_chart_blocks.note_updated_at`), deletes the rows of notes that no longer hold a chart,
  then freezes up to `FREEZE_BUDGET` (10) pending blocks. The block routes call it, so the
  index is read-your-writes. A trashed note keeps its rows and every read hides it. A
  hard-deleted note loses its rows and its ledger rows.
* **The freeze.** Computed once from bars as of the block's day. A re-save, a catch-up, a later
  nightly or a later formula change never rewrites it. Changing a block's symbol or day makes
  it a different chart with its own freeze, and an undo brings the old one back. A fingerprint
  that carries a transient code is not frozen and is retried. When the note itself carries
  `ta.fingerprint`, that copy is served (`fingerprintSource: "note"`).
* Both tables are in `account_purge._DIRECT_USER_TABLES`. They are not address-space objects:
  they have no name column, so `address_space.saved_object_tables` does not count them.

## 3. The API (every route: flag-gated 404 before the session, then a paid plan)

| method | path | answers |
|---|---|---|
| GET | `/api/j2/notebook-fingerprint/meta` | `{version, fields, missingReasons, transientMissing}` |
| GET | `/api/j2/notebook-fingerprint/compute?symbol=&asOf=` | `{fingerprint}`, live and not stored. 422 for a bad symbol, a malformed day or a future day; 503 when a store cannot be read |
| GET | `/api/j2/notebook-fingerprint/blocks?symbol=&setupTag=&noteId=&limit=` | `{blocks, count, pending}`, newest day first, at most 200 |
| GET | `/api/j2/notebook-fingerprint/blocks/{note_id}/{embed_key}` | `{block}`. Another member's note is the one 404 |
| POST | `/api/j2/notebook-fingerprint/blocks/{note_id}/{embed_key}/freeze` | `{block}`, frozen now from the note's own symbol and day. Idempotent |

A block: `{noteId, noteTitle, embedKey, embedId, position, symbol, timeframe, asOf, setupTag,
mode, fingerprint, fingerprintSource ("note" | "ledger" | null), frozenAt, values}`, where
`values` is `summary_values(fingerprint)`.

**How 13I-2 uses it.** After inserting a chart and the note's save landing, POST `.../freeze`
for the new block. Write the returned `fingerprint` into `ta.fingerprint` (13H-1's attr) only
through the member's own save path, never from a projection. The panel reads `fields` and
renders `missing` with the `meta` sentences. The playbook grid reads `GET .../blocks?setupTag=`.

**How 13J uses it.** Templates are `GET .../blocks` rows with a frozen fingerprint. Distance
reads `summary_values` on both sides, and today's names come from `screener_rows`, which carry
the same column names. The nightly job must never call `compute` per universe name: the row
already holds every column except `pct_vs_sma10` and the base.

## 4. Decisions (the lane's own, for the controller)

1. **Distance from the 10 is the 10-day SIMPLE average** (`_sma` + `_pct`), the same shape as
   the stored 20/50/200. The scanner's EMA-10 relation lives in `ema_stack_intact`.
2. **Patterns are the confirmed verdicts, not `screener_rows.pattern_engine_ids`.** Those ids
   are the raw rule-engine detections, and the plan requires `confirmed_only`. A day before
   the confirmed window reads `patterns_current_window_only`. That covers every past insert
   and is a limit 13I-2's suggestion feature inherits.
3. **Nightly or bars, one as-of for every field.** The nightly row is used when no stored
   session lies between its `bars_asof` and the requested day (without bars: at most 4
   calendar days of lag). Then the whole fingerprint is as of the row's day, including the two
   columns computed on bars cut there.
4. **The projection is a catch-up, not a save hook.** The plan's "projection job (watermark),
   never in the save path" and the brief's "maintained as a projection when notes save" are
   both met: the save path's sidecar decides what changed, and the block routes catch up
   before reading. A scheduled `catch_up` for every member is not registered. 13J's nightly
   job or the integrator can call `chart_blocks.catch_up` per member.
5. **A read failure raises; only a missing table is absence.** A store that cannot be read
   answers 503 and is never frozen as `no_bars` (that would be a permanent false "missing").
6. **Paid on every route**, because the fingerprint carries the Screener's columns and the
   pattern engine's confirmed verdicts, both paid surfaces.
