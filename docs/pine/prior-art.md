# Lane 5 — Prior Art: Running / Rendering Pine Script Outside TradingView

**Research date:** 2026-09-08
**Authority:** READ_ONLY_RESEARCH. No repo cloned, no third-party code downloaded, no project file touched.
**Method:** WebSearch sweeps + WebFetch of repo pages, `api.github.com` metadata (authoritative for license SPDX / `pushed_at` / stars), raw `LICENSE` files, and each project's own limitations/parity docs. GitHub **code** search returned HTTP 401 (auth required), so no code-level grep sweeps were possible — repo listings and file sizes were used as the proxy for real code volume.

**Items assessed: 34** (24 code projects + 6 charting/host targets + 4 LLM services)

---

## 1. HEADLINE VERDICT (read this first)

**Prior art materially shortcuts the RUNTIME and the STANDARD LIBRARY. It does essentially nothing for the RENDERER.**

Three things fell out of the search that reframe the build:

1. **The parser is not the hard part, and the market already knows it.** In *every* serious project, the runtime is given away and the parser/compiler is the monetized half:
   - PyneCore runtime = Apache-2.0; PyneComp compiler = closed SaaS ($8–$45/mo).
   - `pineforge-engine` = Apache-2.0; `pineforge-codegen` = PolyForm **Noncommercial**.
   - PineTS = AGPL-3.0 (poison for a SaaS) with a $1,199/dev/yr commercial escape.

   That pricing structure is the market telling you where the expensive work is: bar-by-bar semantics, stdlib numeric parity, and a defensible parity oracle — not lexing.

2. **Nobody has solved rendering.** Every single engine stops at *"here are arrays of numbers."* PineTS's own docs: *"What comes back is just arrays of numbers your code can use."* PineForge: *"PineForge ignores drawing commands (`plot`, `label`, `bgcolor`). It is a backtest engine, not a charting platform."* resin: *"No charting capability — computes values only."* The full Pine visual layer — `plot` styles, `plotshape`/`plotchar`/`plotarrow`, `fill`, `bgcolor`, `barcolor`, `hline`, and `label`/`line`/`box`/`table`/`polyline` with `xloc`/`yloc`/`extend`/`size` semantics, overlay-vs-pane, `scale`/`format`/`precision`, and TradingView's drawing-count ceilings — is **unclaimed prior art**. The only two attempts are `resin-lightweight-charts` (**34 KB**, 0 stars — a demo adapter, not a renderer) and LuxAlgo's Vela + `vela-pinets` (AGPL on the Pine half).

3. **Only two projects have a real TradingView oracle.** This is the single most important honest finding, and it cuts against most READMEs:
   - **pineforge-engine** — TradingView's own exported trade lists as ground truth; *"2,819,967 TradingView trades evaluated, 2,817,481 matched by the verifier (99.91%)."*
   - **PyneSys** — *"564/564 real TradingView scripts compile & run"*, *"99.68% of 69.2M compared bars bit-exact vs TradingView."*

   Everyone else self-certifies. **PineTS's `tests/compatibility/` suite is a self-regression harness, not a TV parity check** — its own README says the goal is *"ensure future changes don't break existing functionality"*, and it covers only **3 namespaces** (`ta`, `math`, `array`) with ~64 cases. **piner** cross-checks its own two backends against each other (two backends by one author share one misunderstanding — that fixture cannot distinguish). **resin** diffs against its own separate Python implementation. **pine-transpiler**'s `DIFFERENTIAL_PARITY_REPORT.md` is 25 scripts with an unnamed oracle. Treat all of those as consistency rails, not parity evidence.

**Direct answer:** This is **not** a from-scratch build for the runtime — there are 3–4 Apache-2.0/MIT codebases you can legally read, learn from, and vendor, and doing so could plausibly save months on the ~300 `ta.*`/`math.*`/`str.*`/`array.*` semantics and the series model. It **is** effectively a from-scratch build for the renderer, and the parity oracle you'll need to trust any of it does not exist in permissive form — you have to build the harness yourself.

## 3. NEGATIVE RESULTS (searched, found nothing credible)

These are load-bearing findings, not gaps in the search.

- **No usable tree-sitter grammar for Pine.** Exactly one exists (`kvarenzn/tree-sitter-pine`): v5-only, highlighting-oriented, **no LICENSE file**, dead since May 2024, 5 stars. If the team wants tree-sitter, they write it.
- **No official TradingView grammar for any modern Pine.** Only `@version=2` ANTLR v3 lexer + parser grammars, in the *archived* v3 docs, under TradingView copyright. Nothing for v3/v4/v5/v6 — the v5/v6 language (namespaces, UDTs, methods, enums, `varip`, matrices, maps, libraries) has **never** had a published grammar.
- **No open-source Pine → ThinkScript / MQL4 / MQL5 / NinjaScript / EasyLanguage / cTrader converter of any kind.** That entire category is Fiverr freelancers at $100–$150 per script, LLM wrappers (Pineify), and blog-post migration guides. Searched repeatedly; there is no engine, not even a partial one.
- **No mainstream backtesting framework claims Pine compatibility.** Backtrader, vectorbt, QuantConnect LEAN, NautilusTrader — all positioned as *alternatives* to Pine, none as compatible with it. The "Pine-compatible backtesting" search space collapses entirely onto the six engines in the table above.
- **No project renders Pine's full visual layer.** Zero. The closest permissive artifact is a 34 KB, 0-star adapter handling plots/markers/candles/hlines.
- **No evidence of TradingView legal action** against any reimplementation. TradingView owns the **Pine Script®** trademark and asserts blanket IP over its platform content; several projects defensively self-describe as *"clean-room… derived exclusively from public TradingView documentation"* (piner) or note their community-script test corpora stay private *"under TradingView's Terms of Service"* (pineforge). **Implication:** clean-room-from-public-docs is the established norm and the trademark is the live risk — avoid "Pine Script" in a product name; describe compatibility, don't claim the mark. (Not legal advice.)
- **GitHub code search was unavailable** (`api.github.com/search/code` → HTTP 401). Repo/topic/metadata search was thorough; a code-level sweep for niche one-file grammars could still surface stragglers, but nothing in the topic pages (`pine-script`, `pinescript`, `pinescript-v6`, `pine-script-v6`) suggests a missed major project.

## 4. WHAT IS ACTUALLY WORTH TAKING — conservative

Ranked by (license cleanliness × real value). `uct-dashboard` is a commercial network service, so **AGPL is disqualifying** for anything linked into it.

### Tier 1 — legally clean, genuinely useful

1. **PyneCore `src/pynecore/lib/` — Apache-2.0. Best stdlib-semantics reference available.**
   `ta.py` at 121 KB is the densest correct-by-construction Pine TA implementation you can legally read, and it is backed (indirectly) by the only 69.2M-bar TV parity number in the industry. `array.py`, `matrix.py`, `string.py`, `request.py`, and the drawing modules are all there. **Use it to settle semantics questions** ("what exactly does `ta.rma` do on the first bar?", "how does `array.slice` alias?"). Porting individual function bodies TS-ward under Apache-2.0 attribution is defensible. Caveat: it's Python; the front end is not included.

2. **`pineforge-engine` — Apache-2.0. Only credible source of truth for execution/order semantics.**
   If Pine `strategy()` backtesting is ever in scope, do not re-derive fill/sizing/margin/trailing-stop rules — read this. Its **validation harness design** (TradingView trade-list exports as oracle, graded excellent/strong/moderate/weak, 4,190 scored probes) is the most transferable idea in this whole report and directly answers "how would we ever know we're right?" **Steal the methodology even if you never touch the C++.**

3. **`Opus-Aether-AI/pine-transpiler` — MIT. Best small parser to learn from.**
   ~64 KB of hand-written lexer + recursive-descent parser + expression parser is the right size to read end-to-end in a day, and `docs/LIMITATIONS.md` is a ready-made checklist of what a Pine parser must decide about. MIT means you may vendor it. **But do not vendor its runtime** — `stub-namespaces.ts` + `mock-factories.ts` is the tell. Take the front end, write your own back end.

4. **LuxAlgo/Vela — Apache-2.0. Render substrate worth a serious evaluation.**
   Swappable renderer/data/scripting ports plus 70+ indicators and drawing tools, commercially free. Realistic path: **Vela's Apache-2.0 core + your own Pine bridge**, deliberately *not* `vela-pinets` (AGPL). Discount hard for age — 8 weeks old, expect breaking changes.

5. **`yankikucuk/pine-script-syntax-highlighter` — MIT. Free current v6 keyword/builtin inventory.**
   Low glamour, real time saved: an MIT-licensed, actively updated enumeration of the v6 surface. Good input for a completeness checklist.

### Tier 2 — high potential, needs an audit before you trust it

6. **`nullarch/resin` — Apache-2.0. The closest thing to "the thing you're building," already permissive.**
   Compiler + runtime + drawings + strategy + a Lightweight Charts adapter, ~1.3 MB of TS, self-reported 95.1% compile rate on 10,618 real scripts. **Recommendation: timebox a one- to two-day audit before betting anything on it.** Concretely: (a) does `tests/unit/` actually pass, and do those multi-MB files assert real values or just shapes; (b) is the 583 KB `analyzer.ts` maintainable by anyone but a model; (c) spot-check 10 `ta.*` outputs against TradingView by hand. If it survives, it is the largest single shortcut in this report. If it doesn't, you've spent two days and learned the shape of the problem. Do not adopt it sight-unseen — 2 stars and 0 watchers means **nobody else has ever validated it**.

### Tier 3 — read-only reference, never link

7. **PineTS (AGPL)** — the reference *product*, and the benchmark for API surface. Read the docs (`docs.luxalgo.com/developers/pinets/api-coverage`) for a free, well-organized Pine-surface completeness checklist. **Do not link the code.** If the team ever wants to ship fast rather than build, **$1,199/dev/yr is the honest buy-vs-build number** — worth putting on the table explicitly.
8. **`piner`, `pyne`, `pinescription`, `OpenPineScript` (AGPL/GPL)** — architecture reading only. `pynescription`'s bytecode + streaming-evaluation design and `pyne`'s ANTLR4→ASDL→dual-engine pipeline are the two ideas worth stealing at the *design* level.
9. **TradingView's v2 ANTLR grammar** — lexical-layer reference for the parts of Pine that never changed. Read, don't copy.

### Do not touch

`tree-sitter-pine`, `joelmo/pine-js`, `CHANGGELY/pine-script-compiler` (all **no license**); `pineforge-codegen-oss` (PolyForm **Noncommercial**); `revanthpobala/pinescript-vscode-extension` (NOASSERTION, unresolved); `TomCallan/pyine` (archived, trivially shallow despite 133★); every LLM converter service (nondeterministic, no parser, no parity — they cannot be part of an engine).

## 5. THE HONEST GAP LIST — what no prior art gives you

Ordered by how much of the build they represent.

1. **The renderer.** Nothing exists. `plot` styles (line/stepline/histogram/area/columns/circles/cross), `plotshape`/`plotchar`/`plotarrow`, `fill` between plots/hlines, `bgcolor`, `barcolor`, `hline`, `label`/`line`/`box`/`table`/`polyline` with the full `xloc`/`yloc`/`extend`/`size`/`text_halign` matrix, overlay-vs-separate-pane, `scale`/`format`/`precision`, TradingView's drawing-count ceilings and the 64-plot limit. **Assume ~100% from scratch.**
2. **A TradingView parity oracle you own.** Only two exist and neither is permissively licensed. Both were built by exporting TradingView output and diffing — that harness is yours to build, and per the codebase's own hard-won lessons, a rail that cross-checks two of *your own* implementations cannot distinguish a shared misunderstanding. `pineforge`'s graded-probe design is the template.
3. **v6 completeness.** Every project's roadmap has "full v6 compatibility" still open. Nobody has finished it, including the AGPL leader.
4. **`request.*` beyond `security`.** `financial`, `economic`, `dividends`, `earnings`, `splits`, `currency_rate`, `seed`, `quandl` — unimplemented essentially everywhere.
5. **Library `import`/`export` with version resolution.** Only `piner` (AGPL) claims it. Everyone else: *"external library resolution not implemented."*
6. **Intrabar / tick-level fidelity.** resin, verbatim: intrabar fills are *"unconfirmable from OHLC data alone."* A real ceiling, not a project defect.
