## 1 · The manifest contains the module that caused the 65-second ack

```
api.massive_processor        IN MANIFEST
api.services.cap_universe    IN MANIFEST
```

⭐ That is the check that matters: the scanner, run blind over `api/**`, independently names the
module `flow_source` lazily imports. It was not put there by hand.

(`api.services.discord_render.symbols` is correctly **absent** — it is imported at module level,
so it is not a lazy import and costs nothing on first use.)

## 2 · ⛔ BUT THE IMPORT IS CHEAP, AND THE MANIFEST ONLY COVERS IMPORTS

Measured cold, one module per fresh interpreter:

```
api.massive_processor      13.5 ms
api.services.cap_universe   3.8 ms
```

Against a measured **125.9 ms** for `flow_source`'s first *call*. So **~17 ms is the import and
~109 ms is the DATA LOAD** — `cap_universe.etf_symbols()` reading and caching the universe on
first use.

⛔ **The preload manifest as built covers imports, not first-call caches.** Preloading all 502
modules would have removed ~17 ms of the 126 ms and left the rest on the ack path. R63(c)'s
barrier therefore needs **two** lists, not one:

1. the **module manifest** (derived, 502 entries) — import cost;
2. a **warm list** of first-call cache functions (`cap_universe.etf_symbols`, `symbols.warm`, and
   whatever the 1,013 in-function loaders resolve to) — data-load cost.

The scanner names the loader *sites*; turning those into callable warm targets is the remaining
work, and it is the half that actually carried the cost here.

## 3 · ⛔⛔ AND 126 ms IS NOT 65,462 ms. THE HYPOTHESIS EXPLAINS THE SHAPE, NOT THE MAGNITUDE.

| | measured |
|---|---|
| `flow_source` first call, local, idle machine | **125.9 ms** |
| `entry_to_ack`, live pod, first `/flow` after deploy | **65,462.6 ms** |
| ratio | **~520×** |

R63 states the hypothesis as *"a lazy import plus an ETF-universe load on the ack path"*. The
**shape** fits exactly — slow first, 1.4 ms second, and W1b's fix (moving it off the ack path)
returned it to **2.2 ms** under the same boot-window conditions. But the **magnitude** does not:
nothing measured here costs 65 seconds.

⭐ **The reading that fits both is TRIGGER + AMPLIFIER:** ~126 ms of cold work is the trigger, and
a boot-storm pod — `ticker-names-prewarm` over 3,742 tickers, the chart hot-warm overrunning its
20 s budget, `rs_ranking` over 3,696 symbols, the screener sweep, all inside two minutes — is an
amplifier that can stretch a 126 ms task by orders of magnitude while it waits for the GIL and the
anyio pool.

⛔ **That is a hypothesis with no measurement behind it, and it is labelled as one.** It predicts
something testable, which R63(b) should measure directly: instrument first-use so each cold call
logs its own duration *and* whether it ran on the loop thread, then join those against the durable
stall record. If a 126 ms local cost logs as 65 s on the pod, the amplifier is real and the fix is
still the barrier (pay it at boot, when nothing is waiting). If it logs as ~126 ms, then something
else consumed those 65 seconds and the hypothesis is wrong about this incident.

## 4 · One safety defect found in this instrument before it ran

`--measure` imports every candidate module standalone. On this box `/data` exists as `C:\data`, so
a bare `import api.<x>` outside pytest resolves ~72 independent env defaults to **the owner's live
files** — root cause 1 of the 2026-09-08 sandbox incident, re-committed on 2026-09-12 by a probe
that set `DATA_DIR` and believed itself sandboxed.

⭐ Fixed before the first real run: every subprocess applies `conftest.shared_data_root_census()`
— the **derived** pin set, never a hand-picked var — against a fresh `mkdtemp`, and arms the
tripwire, *before* importing anything from `api.**`.

⚠️ And the fix broke the measurer's own control, which is why controls get checked too: the
prelude imports `conftest`, which pulls in `json`, so the original non-vacuity case ("time a real
module") measured an import that had already happened and read **0.0 ms** — passing while
measuring nothing. The control is now `xml.dom.minidom` (85.7 ms) and asserts `> 0.0`.
