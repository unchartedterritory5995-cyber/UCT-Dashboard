## 3 · The cause, and the cause it is NOT

The log line, captured inside the ~35-minute retention window:

```
2026-09-17 14:00:07,740 INFO  discord_render: drender {"evt":"ack","cmd":"flow","hop":"entry_to_ack","ms":12.1}
2026-09-17 14:00:07,740 INFO  discord_render: drender {"evt":"ack","cmd":"flow","hop":"send_to_entry","ms":739.8}
2026-09-17 14:00:07,743 INFO  discord_render: drender {"evt":"shadow","cmd":"flow","ms":1.6,"outcome":"agree","detail":"n=1 refuse=- unans=- idx=1 pre=5"}
2026-09-17 14:00:37,886 WARNING api.routers.discord_interactions: [flow] fetch failed SPY (30): timed out
```

**The read TIMED OUT.** 14:00:37.886 − 14:00:07.740 = **30.1 s**, against
`run_flow_card_job`'s `timeout_s: float = 30.0`. A clean expiry, not an error response.

⛔⛔ **IT IS NOT THE C-14 ETF PARTITION, AND THAT WAS THE OBVIOUS WRONG ANSWER.** The partition
story is true about the code and false about this failure:

- `discord_interactions.py:499` (pre-V2) calls `run_flow_card_job` with **no `source` argument**,
  so the signature default `source: str = "stocks"` applies — confirmed in source, not cited.
  `commands.py:579-584` (V2) computes `symbols.flow_source(tkr)` and passes `etfs`.
- **But a partition miss takes a different branch and says a different sentence.**
  `discord_interactions.py:246-255`: `if not data or not data.get("ok")` → *"the flow feed is
  reconnecting"*; `if not (data.get("contracts") or [])` → *"**SPY** — no significant options
  flow …"*. A `stocks` lookup for SPY returns **`ok: true` with zero contracts** — which is
  precisely what `flow_source`'s own docstring measured: *"0 contracts against 182 under `etfs`
  on 2026-09-13"*.

So the partition would have produced the **second** sentence. We observed the **first**. ⭐ The
discriminator was one grep, and without it "SPY is an ETF in the stocks partition" would have
been published as the cause — plausible, well-supported by two call sites, and wrong.

⚠️ **AND IT LEAVES A REAL OPEN QUESTION, STATED RATHER THAN CLOSED.** On 2026-09-13 SPY-under-
`stocks` *returned* — fast enough to count 0 contracts. On 2026-09-17 the same partition for the
same symbol **times out at 30 s**. Something changed between those dates, or the two readings
were not taken against the same flow-worker state. **This evidence cannot say which**, and the
next step is a flow-worker-side read, not another Discord command.

## 4 · What this establishes, and what it does not

**Establishes:**
- The failure is a **30-second read timeout**, reproducible for SPY across two sessions of the day.
- The ack path is healthy and nowhere near the deadline: **12.1 ms** `entry_to_ack`, 739.8 ms
  `send_to_entry`. C-02 (event-loop starvation taking ack and renderer together) is **not** in
  play here — the ack was fine and the renderer never got data.
- The V2 shadow read `outcome: "agree"`.
- **Row 7 is settled as NOT RUNNABLE on evidence, not by construction.** SMOKE-3.5 left it
  *"INCONCLUSIVE-BY-CONSTRUCTION unless the 10:00 ET run shows §5's shape"*. It did not: the reply
  is the one-line pre-V2 catch-all, which satisfies "never silence" and says nothing about
  04-visual-spec §5's degraded card.

**Does NOT establish:**
- *Why* the read times out. Symbol-specific slowness, a flow-worker-side query without an index,
  and a partition that cannot be satisfied cheaply are all consistent with what is here.
- Anything about row 5. `source=etfs` is unreachable from the pre-V2 dispatch, so this run could
  not have scored it either way.
- Anything about members. V2 is dark; organic exposure remains **0**.

## 5 · The member-facing half, which is the part that matters

⛔ **A member is told the feed is "reconnecting" and to "try again in a moment" — for a condition
that a retry cannot fix, and that has now persisted across three hours and two market sessions.**
The advice is wrong, and it is wrong in the direction that wastes the member's time and hides a
real defect.

This is **C-08 exactly**, already written into `contract.py:12` and `badge.py:156`: this project
*"spent two weeks answering 'the flow feed is reconnecting' to four different causes"* — a 30 s
timeout on 2026-09-11 among them. **Today's failure is the same sentence for the same class of
cause, seventeen days later**, because the fix is `fail_fn` — the V2 failure contract — and V2 is
dark. `run_flow_card_job`'s own docstring states the consequence plainly: *"Without `fail_fn` the
replies are byte-identical to what members get today."*

⭐ **So this run is evidence FOR the V2 failure contract, gathered from the pre-V2 path.** It is
the cleanest argument the programme has produced for why C-08's fix is worth shipping: the cause
was sitting in the pod log the whole time, one word long — `timed out` — and the member got a
sentence that pointed away from it.

## 6 · An instrument finding, recorded because it contaminates a measurement

A second `drender` ack for `cmd:"flow"` appears at **13:54:16Z**, six minutes before the command
was sent:

```
2026-09-17 13:54:16,169 INFO discord_render: drender {"evt":"ack","cmd":"flow","hop":"entry_to_ack","ms":22.9}
```

**No message exists in the channel at that time**, and the staged command was zoom-verified as
unsent at 13:54:3x. The probable reading is that it is the **ticker autocomplete round-trip** —
the `ticker` list is served by this app (dynamic choices), so typing `SPY` must reach it, whereas
`days` is a static choice list and produced no second ack, which fits.

⚠️ **Stated as probable, not established.** If it holds, then **any rate or latency measurement
keyed on `evt:"ack", cmd:"flow"` is contaminated by autocomplete traffic** — inflating arrival
counts and pulling latency down (22.9 ms and 12.1 ms are indistinguishable in that stream). That
would matter to `arrival_census.py` and to any C-02 arrival-rate reasoning. **It is one field's
worth of work to settle** (an `evt` that distinguishes an autocomplete from a command) and it
should be settled before those counts are quoted again.
