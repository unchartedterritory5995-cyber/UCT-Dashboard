# R62 F3 acceptance — first attempt, 2026-09-18 (09:30 ET session)

**Bar, verbatim (D-19 addendum 2):** 10 consecutive `[screener-live]` sweep receipts with
`held_lock_ms < 1,000ms` during today's 09:30-16:00 ET session, and `"maximum number of running
instances reached"` absent from the tailed web log for the same span. Record the ten receipts;

## Verdict: NOT CLOSED today. The gap is named below — it is not a flaw in R62's own fix.

## The "instance collision" alarm was a false alarm — investigated and cleared

The market-open monitor kept firing `INSTANCE COLLISION LINE FOUND`. Direct inspection of the
log (not the monitor's self-report) found exactly **one** real occurrence of the string, at
`2026-09-18 13:04:45,795` (**09:04:45 ET — 25 minutes before today's 09:30 ET open**, outside the
acceptance window entirely) — an `apscheduler` job (`interval[0:01:00]` trigger, unrelated to the
screener sweep) skipped because its previous run was still in flight. That single line appears
**12 times** in the captured `.log` file at different byte offsets, all with the identical
timestamp — a duplication artifact of the log-tail daemon's poll-and-dump capture (`railway logs`
re-dumps its current buffer each 30s cycle rather than tailing only new lines; a quiet period
re-captures the same already-seen lines). Not a new finding — `logtail-continuity-2026-09-18.md`
already documented this mechanism — but this is the first time it was shown to also fool a naive
`grep -q` collision check into repeat-alarming on stale content.

**No instance-collision line was found inside the 09:30-16:00 ET window itself**, in the portion
of the session observed (through ~14:47 UTC / 10:47 ET). That half of R62's bar is clear.

## The `held_lock_ms` bar was NOT cleared — and the cause is now well-evidenced

receipt-count progress at all**: it used `grep -oP 'held_lock_ms=\K[0-9.]+'`, and `-P` (PCRE)
fails silently in this box's locale (`grep: -P supports only unibyte and UTF-8 locales`), so the
extracted value was always empty and the counter never advanced — only the (also-unthrottled)
collision check kept firing, on a loop, forever, which is the noise the earlier status updates
described. Fixed by switching to `grep -oE`, which works correctly in this locale; re-verified by
hand against the raw log lines throughout (never trusted the corrected script's self-report alone
either, per this programme's own rule — the `held_lock_ms` numbers below are quoted directly out

## Root cause: two OTHER concurrent workstreams deployed `web` during market open, each restarting the boot-window tax

`railway deployment list --service web --json`, read directly (not inferred):

| deploy landed (UTC / ET) | commit | what |
|---|---|---|
| 13:46:06 / 09:46:06 ET | `6b15b6b99b` | "D-056: close DC-3 with the post-flip verification on a foreign deploy" — docs-only |
| 14:21:27 / 10:21:27 ET | `cd3c929230` | "Merge branch 'feat/wisdom-loop' into HEAD" |

Both are from other active sessions on this shared repo, unrelated to the D-19 programme. `web`
pushes are policy-permitted "any time" per `deploy-windows.md` ("the FILES decide, not the
clock"), and neither push did anything wrong by that rule. **What this attempt newly measures is
the actual COST of that policy when a push lands during market open**, on THIS specific
instrument (the screener-live sweep lock), independently of R31's own general boot-window
finding:

- **Peak severity is far worse than anything R31 recorded**: 80,068ms and 110,402ms
  `held_lock_ms`, vs. R31's own worst class (`>=5,000ms` events, 7.8/day). A single
  screener-sweep call, mid-market-open, held the lock for **almost two full minutes** on the
  second episode.
- **The settle tail is longer than R31's characterized boot window.** R31 measured "boot (0-15
  min)" as the elevated-rate zone. Episode 1 did not reach three consecutive clean sub-1,000ms
  receipts until **~20 minutes** post-boot (pod booted ~13:49:47 UTC per `/api/health` uptime
  arithmetic; settled at 14:09:16 UTC). Episode 2 was still not cleanly settled after **~21
  minutes** (pod booted ~14:26:21 UTC; still 1,037-1,184ms, just over the bar, at 14:46-14:47 UTC).
- ⚠️ **n=2 boot events. This does NOT establish a new universal boot-window duration** — the
  original caution about two points not establishing a rate applies exactly here. What it DOES
  establish, concretely and reproducibly from real log content: on at least two occasions, a
  market-open-adjacent web redeploy produced a screener-sweep degradation lasting materially
  longer than 15 minutes and peaking well past 60 seconds — worth a wider sample before treating
  either number as a ceiling.

**This is not a regression in R62's fix — verified against the actual deployed code, not
inferred.** ⛔ A near-miss worth recording: this worktree's OWN checked-out branch
(`discord-render-hardening`) does NOT carry R62's fix (`546a5d3ef` is not an ancestor of this
branch's HEAD — R59 deliberately keeps this branch's runtime invariant, so it was never merged
here, correctly). Reading `api/services/screener/live_tier.py` IN THIS WORKTREE would show the
pre-fix 3-argument `_sweep_locked(receipt, ymd, scan_volume)` with the network fetch still
inside it — which is NOT what is running in production. `origin/master` (what Railway actually
deploys, confirmed via `railway deployment list`) carries the real fix: `full_market_snapshot()`
is fetched into `snap` BEFORE `_BUILD_LOCK.acquire()`, and handed into the now-4-argument
`_sweep_locked(receipt, ymd, scan_volume, snap)`. Checked directly with
`git show origin/master:api/services/screener/live_tier.py` — the fix is there, byte for byte,
exactly as `546a5d3ef`'s diff describes.

**So what IS ballooning to 80-110 seconds, if not the network fetch?** The receipt's own
`held_lock_ms` and `duration_ms` were essentially IDENTICAL at the peak (`110402.12` vs
`110402.39` — a 0.27ms difference) in the raw log line. Since the fetch happens BEFORE
`t_held` starts timing (and is itself timed separately into `receipt["snapshot_ms"]`, per R62's
own commit), `duration_ms ≈ held_lock_ms` can only mean the pre-lock fetch cost (`snapshot_ms`)
was near-zero for that call — i.e., `full_market_snapshot()`'s own 30s cache was warm — and
**the entire 110 seconds was spent inside `_sweep_locked` itself**: `_read_anchor_rows()` +
the ~3,745-row derive loop (`cols_recomputed=95996` on that cycle) + the write. That code path
was never R62's target and was never claimed to be fast under contention — R62's own baseline
(122ms median) was measured on an otherwise-idle process. **This is therefore a genuinely new,
previously-unmeasured finding**: the LOCKED derive-and-write section itself, not just the
now-fixed network fetch, is vulnerable to a boot-window-scale slowdown (CPU/thread/IO contention
from the several other prewarm jobs racing on the same anyio threadpool right after a redeploy),
and R62's fix does not reach it. Worth a follow-up measurement (does `_read_anchor_rows` or the
per-row derive loop dominate?) if this recurs — not attempted here, given the OOM pressure this
box was already under while gathering the numbers above.

- Whether the ~20-minute settle tail is specific to market-open load (highest feed_symbols/volume

- Whether a THIRD, independent workstream's push pattern today is itself worth flagging upstream —

  cost, even though each one is individually policy-compliant.

## Recommendation

- **Do not touch R62's own code.** Its fix is doing exactly what it was built to do (verified
  against `origin/master`, not this branch); the baseline numbers prove it, and the fetch is
  confirmed outside the lock.
- **A new, un-filed candidate exists for whoever works R63/boot-window next**: the locked
  `_sweep_locked` body (anchor read + ~3,745-row derive + write) itself degrades to 80-110s
  under boot-window contention, independent of the (already-fixed) network fetch. Not
  root-caused here — only localized to inside vs. outside the lock via the `held_lock_ms` ≈
  `duration_ms` identity. This is a plausible NEW OI-44/boot-window contributor worth a look.
- **Retry F3 acceptance later today** (after 14:47 ET, once/if the market-open deploy churn
  settles) or first thing next session — the bar itself (10 consecutive, <1,000ms, no in-window
  collision) is very likely achievable once no further mid-session `web` deploy interferes.
- **Worth a policy note, not a code change**: this is the first CONCRETE measurement of what a
  market-open-adjacent `web` redeploy actually costs a live, latency-sensitive code path — up to
  ~20 minutes of degraded performance, peaking past 60-110 seconds on a single call. If this
  programme wants a stronger claim than `deploy-windows.md`'s current "~1 min blip," this attempt
  is the evidence for it — but that is a decision for whoever owns that doc, not something this
  attempt should silently change.
- ⛔ **Read from `origin/master` (or a deployed pod), never from `discord-render-hardening`'s own
  checkout, when investigating what is actually RUNNING.** This branch's R59 invariance is
  deliberate and correct for the hardening programme's own purposes, but it means this worktree's
  files are NOT what production is executing — caught here before publishing a false "the fix
  regressed" claim; recorded so the next session investigating live behavior from this worktree
  doesn't make the same mistake.
