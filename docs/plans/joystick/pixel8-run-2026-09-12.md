Device: **Google Pixel 8, Android 14, Chrome** (BrowserStack Live).

## ✅ What this run DID establish, and it is worth having

⭐ **TalkBack is available and drivable on this device**, which is a real difference from iOS and
corrects an assumption the sheet could otherwise have carried. BrowserStack's left panel offers
**Screen Reader** with the description *"provides spoken description of your web page for
Accessibility Testing using Google TalkBack"*, and the toggle worked in **both** directions —
"Screen Reader has been enabled successfully" then "…disabled successfully".

⛔ Compare iOS, where the same control answers *"Screen Reader is currently not supported for this
device"*. So **G2-3 / G2-4 are blocked by the PLATFORM** and **G2-1 / G2-2 are blocked by something
else entirely** — below. Those are different facts and the sheet should not blur them.

## ⛔ Why the rows could not be run: the device cannot be authenticated

Two independent transport failures, both measured, neither a product fault:

**1. The Android mirror loses CAPITALISATION when typing.** Typing the login URL into Chrome's
address bar produced, read back off the device:

```
intended:  .../smoke-login#token=thv8CFeTT8786rRI3sGUWFyQHKb8Ep4OK4PxBFozzXw
landed:    :786rri3sguwfyqhkb8ep4ok4pxbfozzxw
```

Every capital is gone and characters are dropped. The token is **base64url and case-sensitive**, so
it can never be typed correctly on this device. ⭐ An earlier attempt landed
`uctintelligence.com/smc` — the path itself corrupted. iOS typed the same URL correctly; this is
Android-mirror-specific.

**2. BrowserStack's `url=` session parameter is overwritten by its own session state.** The
documented way to avoid typing is to launch the session with the URL preloaded. Tried twice: the
first time the parameter was ignored because the session already existed; the second time, after
stopping the session and relaunching with a freshly minted link, BrowserStack **replaced my URL
with the previously typed, mangled one** — visible in its own address:
`...%2Fsmoke-login3token%3Dv902-bzgqgtqcd6du8nbydvpknwjel-pxmke9y2x6a`.

⛔ **No third attempt** — the owner's rule is two per row.

⛔ **And the one remaining route is closed by standing rule:** typing the account's password into
the device. An agent does not type passwords, which is the entire reason the login link exists.

## ⚠️ A hardening limitation this run exposed

The token rides in a URL **fragment** so it never reaches a server. But **BrowserStack's Live client
copies the whole typed URL, fragment included, into its OWN dashboard query string**
(`live.browserstack.com/dashboard#...&url=https%3A%2F%2F...%23token%3D...`). That was already within
the accepted risk — the programme has always accepted that the token "lands in their session
recording" — but it is worth stating plainly that the fragment protects against **our** logs, CDNs
and search engines, and **not** against BrowserStack itself. With a 2-minute single-use token on a
synthetic account, that remains acceptable; it would not be for a real account.
