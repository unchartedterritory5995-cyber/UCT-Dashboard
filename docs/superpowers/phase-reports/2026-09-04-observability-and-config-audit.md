### Recorded-but-never-rendered / rendered-but-never-producible — found this session

1. **`SourceRow.jsx::freshnessLabel` has no branch for `lastSyncStatus === 'error'` when the source isn't `broken`.** (`app/src/pages/journal-2-0/components/connectors/SourceRow.jsx`, the `freshnessLabel` function, ~line 25-40 — **not my file to edit**, reporting only.) Reproduction: any exception besides `NoteConnAuthError` (a bare `NoteConnTransient`, `NoteConnRateLimited`, or an unrelated bug) reaching `_do_sync`'s outer `except` (engine.py:607-621) sets `status='active'`/`lastSyncStatus='error'`/`lastSyncAt=now()` — proven live today by the pre-existing `test_provider_exception_marks_log_error_and_does_not_advance_cursor`, which already asserts `lastSyncStatus == "error"` with no accompanying `broken` assertion. `freshnessTone` correctly turns the dot red for this case, but `freshnessLabel` falls through every branch to `if (source.lastSyncAt) return 'synced ${timeAgo}'` — a **red dot next to a label that says the sync just succeeded**, which is worse than silence: it's dot-vs-text contradiction on a state that legitimately failed. The 'warning' branch got this exact fix in the A1 fix-round; 'error' (non-broken) never did.
2. **`freshnessTone` never reads `lastSyncError`/`failures`.** A partial per-note failure (#3/#7/#8/#10 above) keeps `status="ok"`, so the dot stays green while an error paragraph renders underneath — internally consistent with the "the batch committed what it could" design intent, but worth the owner knowing it reads as "green + an alarming red-tinted line" rather than "amber, with detail."
3. No shape of the *opposite* defect (a backend-unreachable state with a live UI branch) was found this session — the original `'warning'`-status branch that motivated this task is now reachable, tested, and its A1 root cause (per-note SAVEPOINT isolation, `notes.py:513`) is real and green.

### Rule-by-rule verification (each proven by execution)

1. **No false "success" on zero-landed** — `test_a_pass_that_stores_nothing_persists_warning_and_why` (existing) proves `status="warning"` both in the return value AND the persisted row for a 100%-fetch-failure pass. PASS.
2. **One bad note ≠ poisoned batch** — `notes.py`'s per-note `SAVEPOINT j2_import_note` (confirmed present, `notes.py:513`); `test_import_confirm_isolates_one_bad_note_and_commits_its_healthy_siblings` + two realistic-scale siblings (`test_notes_import.py:405,528,556`) all pass. Re-verified end-to-end through the ENGINE (not just `notes.py` directly) by the new test this session. PASS.
3. **Cursor never advances past a note that didn't land** — was previously proven only for the *total*-loss case (indirectly, via status). The *mixed* case (one lands, one doesn't, the un-landed one is chronologically newer) had **zero coverage anywhere in the repo** — no test referenced `not_stored_refs`/`notStoredRefs` at all. Added `test_a_real_oversized_note_is_isolated_and_holds_the_cursor_back` (`test_note_connectors_engine.py`, appended after line 1896): 2 refs, one ordinary note (creates), one genuinely >1MB doc through the real `import_confirm` validation (not a mock). Asserts the healthy note lands, the oversized one doesn't, neither poisons the other, and `cursor is None` afterward even though the oversized note is the newer ref. **Verified non-vacuous**: reverting the `if not not_stored_refs:` guard to `if True:` in `engine.py` made this exact test fail (`cursor advanced`); guard restored, test green again. PASS, now with a rail that didn't exist before today.
