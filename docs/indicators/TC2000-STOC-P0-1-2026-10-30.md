# TC2000 `STOC` — audit P0-1, 2026-10-30

Branch `fix/indicators-tc2000-stoc`. Draft PR only; nothing merged or deployed.

## What was wrong

`app/src/components/chart/engine/ast/pcf.js:196` (at `f5ae43ec2a`) declared
`STOC: { fn: 'stoch', series: ['close', 'high', 'low'], … }`. The manifest's
`stoch` is `args: [series, series, series, int]`,
`argRoles: [high, low, close, period]` (`closedTable.json` `functions.stoch`),
and the browser binds it as `stoch: (h, l, c, n)` (`interpret.js:2768`). So
`STOC14.3` became `sma(stoch(close, high, low, 14), 3)`. That is
100·(L − lowest(H))/(highest(C) − lowest(H)), not a stochastic. It was labelled
an exact import.

The order came from prose rather than data. `_functions_indicators` in
`closedTable.json` still says `stoch(source, high, low, length)`, which is
Pine's `ta.stoch` shape and not this table's. That sentence is stale. It is
**not** edited here, because `closedTable.json` is another lane's file this
session. Flagged for the manifest owner.

## TC2000's semantics (primary source)

- help.tc2000.com/m/69445/l/755874, "Stochastic Oscillator":
  *"K = ((C - Ln)/(Hn - Ln)) * 100"*, where *"C is the latest closing price"*,
  *"L is the n-period low"* and *"H is the n-period high"*. The page's PCF table
  gives `STOCx.y.z`, Slow %K `STOCk.3.z`, and %D `AVG(STOCx.k.z, d)`.
- help.tc2000.com/m/69445/l/745531, PCF syntax table:
  `STOC(x, y, z)` — *"x=Period, y=SMA, z=Offset"*.

So the correct reading is `sma(stoch(high, low, close, x), y)`, offset by `z`.
That is exactly the shape the reader already built, apart from the series order.

**Not established:** the value TC2000 shows when the n-bar range is flat
(Hn = Ln). The published formula divides by zero there. This engine answers 50.
No parity claim is made for that case.

## What changed

1. **New imports read correctly.** `STOC` series are now `['high', 'low', 'close']`.
2. **The class is railed.** `checkSeriesRoles` refuses any fused family whose
   fixed series disagrees with the manifest role at that slot. `checkSignature`
   compared kinds only, which is why the rotated order passed.
3. **Saved definitions keep computing what they computed.** `defSchema` re-reads
   `compute.source` and refuses a pair whose hashes differ, so the reader fix
   alone would have failed validation for every saved `STOC` definition, while
   alerts and scans kept evaluating the stored tree.
   - `pcf.js::legacyPcfReadings(source)` returns the tree the pre-fix reader
     built (a pure rotation of every `stoch(high, low, close, n)`).
   - `defSchema` accepts a stored tree that is exactly that reading, on both the
     `compute.source` rule and the per-tree `compute.sources` rule.
   - **No stored tree is rewritten. This is a reading, not a migration.**
4. **Disclosure.** `defSchema.legacyComputeReadings(def)` names a legacy reading.
   The builder shows `PCF_STOC_LEGACY_NOTICE` when such a formula is reopened.
   **An ordinary save keeps the stored legacy tree** (owner ruling 2026-10-30,
   `builder/legacyReadingPin.js`): an unchanged legacy source is pinned to the
   tree it was saved with. The corrected tree is adopted only through the
   notice's **Switch to TC2000's calculation** button, which asks for
   confirmation and warns that values and alerts will change. Editing the
   formula text of a legacy definition asks the same confirmation before it
   saves. The switch is a maths change: a new `astHash`, so it follows the
   existing rev and semantics path for a maths edit.

## Sibling defect found from the same source: TC2000 `ATR`

The syntax table (help.tc2000.com/m/69445/l/745531) lists `ATR(x, z)` as
*"Average True Range (uses simple moving average for smoothing)"*. The ATR page
(help.tc2000.com/m/69445/l/755843) writes every other average as
`tAVG(ATR1.z, x)`, and writes Wilder's smoothing as `XAVG(ATR, 27)` for a 14-bar ATR.

- **Old behaviour.** `pcf.js` mapped `ATRx` to the engine's Wilder `atr`.
- **Correct reading.** `ATRx` = `sma(TR, x)`, where TR is the largest of
  high − low, |high − close[1]| and |low − close[1]|. `ATR1` is TR itself.
- **Not established.** TC2000's true range on the first bar of history, where
  there is no previous close. Here that value is not computable, so the first
  `ATR` value lands one bar later.

This was fixed in the same change and in the same way:

- `ATR` is now an expansion (`PCF_EXPANSIONS.ATR`).
- The one legacy reading, `pcf-reader-before-2026-10-30`, reproduces both old
  mappings together. They shipped together, so no saved tree mixes the two.
- The notice names whichever of `STOC` and `ATR` the source actually uses.
- `doorCoverage.test.js` holds a ratchet on how many engine functions PCF
  reaches. It moved 33 → 32, because `atr` was reached only through the wrong
  mapping. A new assertion pins that `atr` is no longer reached.

The ATR test is a value check against an independent simple average of TR over
1, 5 and 14 bars, plus offset. A control confirms Wilder's ATR gives a
different number.

## Import gap closed on this branch: the function forms

TC2000's syntax table publishes every fused indicator twice, with the same
parameters in the same order: `STOC(x, y, z)` / `STOCx.y.z`, `ATR(x, z)` / `ATRx.z`,
`MACD(s, l, z)` / `MACDs.l.z`, and so on.

- **Before:** the function forms were refused as "not a TC2000 name".
- **Now:** each call is rewritten to its shorthand and read by the one fused
  reader, so the two spellings cannot disagree.
- Every argument must be a written whole number. A computed or fractional
  argument is refused (`pcf:window`), with the shorthand named.
- The function form is detected as TC2000 only in upper case (`ATR(`), so the
  native `atr(` stays native.
- `RSI` and `WSTOC` remain refused with their own reasons.
